## Block H — The Agent Gateway (agent-native reorientation, SH74)

- **SH134** — **`post.move`**, the seventh op. The vocabulary could create, update and delete an address but not *change* one, and the workaround an agent reaches for first — upsert at the new address — creates a second post and orphans the original with its id, its SH51 audit trail and its SH14 version history. `post.move` re-addresses in place ([ShPostUnifiedWriteService#move](../shio-app/src/main/java/com/viglet/shio/migration/unified/ShPostUnifiedWriteService.java), [ShAgentBatchService#postMove](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAgentBatchService.java)) with a new `to` field on `ShAgentBatch.Op`. The design calls: (1) **both state rows move together** — moving only the draft would leave the live page at the old URL while every draft-preferred read reported the new one, so a published post's live URL changes *without a publish step* and the change set says `the live URL changes immediately` rather than letting the human find out (P7); (2) **source absent + destination present is a `noop`** — a move is the one op whose precondition its own success destroys, so without this rule no document containing one could be applied twice, and SH82's re-runnability would be a lie; (3) **never overwrites** an occupied address and **never crosses a site boundary** (separate folder trees, ACLs and tenants), both teaching errors naming the honest two-step; (4) the destination folder resolves its owning site via SH128's walk, so a move into a nested folder does not blank the post's site. Inbound `ShReference` rows are id-keyed and survive; URLs written into another post's body as prose do not, and SH100 is where that gets caught. Manifest flag `postMove`. 9 tests in [ShAgentMoveAndPruneTest](../shio-app/src/test/java/com/viglet/shio/api/agent/ShAgentMoveAndPruneTest.java). → IMPROVEMENTS §VIII.7.
- **SH136** — **byte stability is a build guard** ([ShByteStabilityLintTest](../shio-app/src/test/java/com/viglet/shio/api/agent/ShByteStabilityLintTest.java) + [ShStableMap](../shio-app/src/main/java/com/viglet/shio/utils/ShStableMap.java)). SH130 caught `tools/list` serializing differently on every boot; this generalizes it, and **the generalization found four more live instabilities on the day it was written** — the same yield SH122 and SH128 produced, which is now three guards running.
  <br>**The reason this had to be a lint is the finding worth keeping.** `Map.copyOf`/`Map.of` iterate in an order derived from a salt `ImmutableCollections` initialises **once per JVM**, so the obvious assertion — build the payload twice, compare the bytes — *passes over broken code in every test process there will ever be*. It is the same shape of tautology SH130 deleted from the version check: an assertion that cannot fail at the moment it has a job to do. So the guard is textual, per §VIII.10, with a `byte-stable-exempt: <reason>` hatch (one site uses it: a keyed lookup that is never iterated).
  <br>**What it found.** Five `Map.copyOf` call sites, four of them defects, every one the identical shape: build a `TreeMap` or `LinkedHashMap` *deliberately, for determinism*, then discard that order in the return expression. Ranked by damage: **SH101's render digest** hashed landmarks in map-iteration order, so the same page hashed differently after a restart — and *only for a single-field post*, because the multi-field path re-sorts on merge, which is half-broken determinism and worse than none (the first counter-example reads as a real change). Then the **MCP error `data`** — the payload whose entire job is to teach — reordering `fix`/`allowed`/`didYouMean` per boot, and uncanonicalized at the writer besides. Then SH103's diagnostics counts and SH109's review summary, both of which feed SH116 ETags that would stop matching after a restart.
  <br>**Two fixes, not one.** `ShStableMap.copyOf` preserves whatever order the source had, and the digest now **sorts at the hash site** rather than trusting its caller — because a hash is the one place "the caller sorts it" is not good enough: the failure is a wrong answer, not an exception. That second fix is what makes the per-payload assertion *deterministic*: hand `digestOf` the same landmark counts in deliberately reversed order and require the same digest. **Verified by breaking it** — reverting the sort makes that test fail (`d:635ab9de…` vs `d:99b6b8ef…`), which is the check every guard in this block should have to pass before it is trusted. 4 tests. → IMPROVEMENTS §VIII.11.
- **SH137** — **`folder.move`**, the ninth op ([ShFolderWriteService#move](../shio-app/src/main/java/com/viglet/shio/api/folder/ShFolderWriteService.java), [ShAgentBatchService#folderMove](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAgentBatchService.java)). SH134's defect one level up and strictly more destructive: without it, renaming a section meant `folder.upsert` at the new path plus `folder.delete` of the old, and that delete cascades over every post beneath it — where the post-level workaround orphaned one page, this one destroyed a subtree. SH134 is also what made the gap conspicuous, since an agent that has learned `post.move` will assume the folder verb exists. Takes `to` as the whole name chain (that is what addresses a folder, SH79); the last segment is the new name, so rename and relocate are one op. Manifest flag `folderMove`.
  <br>**No post's URL changes, and that is why it needs no confirm token.** A friendly URL is unique per site and independent of the folder chain, so the pages inside a moved section keep the addresses they had — the opposite of a path-shaped CMS, worth stating because it is the assumption a caller brings. Nothing is destroyed and nothing goes dark, so the op is deliberately **not** in `DESTRUCTIVE_OPS`: it is the safe verb that exists to replace the destructive workaround, and making it demand SH108's two-step would push callers back to what they were doing. The folder's own `furl` *does* follow a rename, unlike a post's (SH139) — a post's is its address and its live URL, a folder's is neither, and deriving it from the name is what `create`, `update` and `folder.upsert` already do.
  <br>**It shipped as one writer both surfaces call, which is SH139's rule paying out — and that is how the live defect surfaced.** The console's own re-parent had no cycle check, and its move dialog navigates *down* from the site root, so a curator could reach a child of the folder they were dragging in three clicks. That does not fail: it succeeds and produces a cycle, detaching the subtree from the root (so every address walk stops finding it) and sending the recursive delete round the loop until the stack runs out — a tree unrepairable through the UI that broke it. Both guards (`ShFolderMoveException.Cycle`, `.Root`) live on the writer so they cannot be present on one path and missing on the other, and `checkMovable` exposes them without writing so a `dryRun` reports what the real run would refuse (SH82: a plan that lied is worthless). Cross-site and occupied-target refusals are shared with `post.move` and are now **kind-aware** — two folders answering one name chain is not the delivery ambiguity two posts on one URL is, and an error describing the wrong consequence teaches something false (P6).
  <br>Adding the op took `tools/list` 3 tokens over its 2200 ceiling; `shio_write`'s description was **trimmed instead of the ceiling raised** (P3: lean the payload first), landing the list back under budget while covering one more verb. The MCP golden's diff is a single line — the op enum — because the goldens collapse free text to type tokens. 8 tests in [ShAgentMoveAndPruneTest](../shio-app/src/test/java/com/viglet/shio/api/agent/ShAgentMoveAndPruneTest.java) plus a console stage in [ShFolderAPITest](../shio-app/src/test/java/com/viglet/shio/api/folder/ShFolderAPITest.java). → IMPROVEMENTS §VIII.7.
- **SH138** — **a deletion plan is never silently shortened** ([ShAgentChangeSet](../shio-app/src/main/java/com/viglet/shio/api/agent/dto/ShAgentChangeSet.java), [ShAgentBatchService](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAgentBatchService.java)). Filed as a truncation hazard; **the truncation was not the live defect, and looking for it found the real one.** Nothing on the plan path cut a row — but plan/apply compile a document into ops and then hand them to the *hand-written batch's* validator, so a prune that swept up 300 undeclared posts failed with `batch-too-large`: "split the work into batches of at most 200 ops". A caller cannot follow that. They never wrote the ops, and a converge cannot be hand-split — so a legitimate large prune, and any `shio push --content` over a tree of more than ~100 posts, had **no path forward at all**. A ceiling with no usable way past it is the same dead end as a silent cut, reached from the other side.
  <br>The fix is the roadmap's two sanctioned options, each where it belongs. **Exempt:** compiled ops get their own ceiling, `shio.agent.batch.max-document-ops` (2000, beside the unchanged `max-ops` of 200), because a document's op count is not a measure of what the caller asked for — a three-post document compiles to four hundred ops when the site holds four hundred undeclared posts. Which ceiling applies is a `Source` argument only `ShAgentDesiredStateService` may pass, deliberately **not** a field on `ShAgentBatch`: on the wire a caller could claim the document ceiling for a typed batch. **Refuse:** past it, a new `document-too-large` teaching 400 names how many of the ops are *deletions* (the number that explains the size) and points at narrowing `folders`, never at splitting batches.
  <br>**And the invariant is now structural rather than observed.** `ShAgentChangeSet`'s compact constructor rejects `results.size() != ops`, so the type cannot express a cut — a guard per §VIII.10 rather than a resolution to be careful, and the thing that will still hold when someone adds a `limit` parameter nobody has thought of yet. The reason a plan gets this treatment while every other unbounded section gets `truncated: true` is that the patterns are not interchangeable: a shortened sitemap reads as incomplete, and a shortened list of deletions reads as a complete review of what is about to be destroyed. The manifest deliberately does **not** publish either ceiling — the agent cannot know in advance how many undeclared posts a prune will find, so the number is only actionable after a refusal, and the refusal carries it (P3: a field paid every session to save one rejected call in a rare case is the wrong trade). 5 tests ([ShAgentDeletionPlanTest](../shio-app/src/test/java/com/viglet/shio/api/agent/ShAgentDeletionPlanTest.java)), including one asserting the unusable advice does not come back. → IMPROVEMENTS §VIII.7.
- **SH139** — **the console move no longer rewrites a post's URL** ([ShObjectWriteService](../shio-app/src/main/java/com/viglet/shio/api/object/ShObjectWriteService.java)). `moveTo` re-slugged `furl` from the title on every move, so dragging a published page between folders silently changed its live URL and discarded any hand-set one — the exact question SH134 spent its design budget on for the agent path, wrong on the path a human triggers by accident. **The fix is a delegation, not a deleted line:** the post branch now calls `ShPostUnifiedWriteService#move`, the code SH134 already got right, so the two surfaces move a post the same way instead of forking on it — which is also what the console was missing (both state rows moving together, `modifiedDate`/`modifier` stamped, and the move landing in the SH51 audit, hence visible to the SH88 feed and the SH109 review queue). A URL is assigned **only when the object has none**, the one case where a move discards no decision; `reparent` stops re-slugging folders for the same reason (a copy still assigns its own). Keeping the URL makes a collision possible on the one move that crosses a site boundary, so that is refused with a teaching 409 (`ShMoveUrlConflictException`, mirroring the agent path's `MoveTargetOccupiedException`) rather than quietly uniquified — which would be the old behaviour in a narrower case. The dialog had no failure path at all, so an unhandled rejection left it open with no explanation; it now surfaces the problem `detail`. 3 stages in [ShFolderAPITest](../shio-app/src/test/java/com/viglet/shio/api/folder/ShFolderAPITest.java). → IMPROVEMENTS §VIII.7.
- **SH135** — **prune covers folders**, not only posts ([ShAgentDesiredStateService](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAgentDesiredStateService.java)). Without it a desired-state document stopped describing its own scope the moment a section moved: the posts went, the empty folder stayed, and the next plan reported `changed:0` over a site that no longer matched the document — which erodes convergence, the only property that justifies declarative apply at all. Scope is unchanged (the declared folders' subtrees; declaring none and asking to prune is still an error). The ordering question — *is a folder prunable while it still holds undeclared content?* — is answered structurally: posts are pruned first and folders **deepest-first**, so a `folder.delete` never relies on its own silent cascade, and a whole emptied subtree collapses in one apply. Three kinds of folder are protected: the declared ones, every ancestor of one, and any folder a declared *post* names as its home (placing a post somewhere is a declaration about that folder too). Manifest flag `folderPrune`. 6 tests. → IMPROVEMENTS §VIII.7.
- **SH128** — **build-time guard for the "site-less object" defect class** ([ShFolderSite](../shio-app/src/main/java/com/viglet/shio/object/ShFolderSite.java) + [ShFolderSiteInvariantTest](../shio-app/src/test/java/com/viglet/shio/object/ShFolderSiteInvariantTest.java)). Only a site's **root** folder carries `shSite`, so resolving an arbitrary folder's owning site means walking to the root; reading `folder.getShSite()` compiles, reviews clean, and silently yields `null` for anything nested. Four copies of the walk existed and a fifth call site was missing it. The guard is a textual lint over `src/main` — any `getShSite()` on an identifier the same file declares as an `ShFolder` fails the build — because a behavioural test proves only the paths it happens to exercise, and the *next* write path is where the next instance lands. **Writing the lint immediately found four more live defects, all fixed here:** `ShAddressResolver#addressOf(ShFolder)` addressed nested folders as `folder:null/…` (an address that resolves to nothing); `ShCdaService#siteIdOf` saw `null` for every non-root folder and `allowsSite(null)` is `false` under an allow-list, so a **scoped CDA token could not list the children of, or resolve the path to, any folder below a site root**; `#buildPath` returned a null site on nested paths; and `ShPreviewTokenAPI`'s folder fallback read only the immediate folder, 404-ing a preview link for any post in a subfolder. Two call sites read the field deliberately (the exchange export records it root-only; the console XP endpoint touches it to force a LAZY proxy) and carry a `ShFolderSite-exempt` comment naming why — an exemption costs a line of prose in review, which is the right price. → IMPROVEMENTS §VIII.10.
- **SH130** — **MCP wire conformance** ([ShMcpWireConformanceTest](../shio-app/src/test/java/com/viglet/shio/api/agent/mcp/ShMcpWireConformanceTest.java) + goldens in `src/test/resources/mcp/golden/`). The behavioural tests would all still pass after renaming `inputSchema`, moving `isError` inside `content`, or answering `resources/read` with `content` instead of `contents` — and every MCP client would break. A hand-rolled protocol has no compiler checking it against the spec. The goldens are **shape transcripts**: every key and its nesting, with the literal value kept for the fields that are themselves contract (`jsonrpc`, `protocolVersion`, `type`, `mimeType`, `role`, error codes, the op `enum`, the method list, and the tool/prompt/resource **names**, which are the public API), while free text collapses to a type token so a copy edit is not a golden update. Regenerate with `-Dshio.mcp.golden.update=true`. The version claim is checked against the **observable obligations** of MCP `2025-06-18` — batching refused, structured capability objects, `serverInfo.title`, `content[]`+`isError` results, plural `contents`, templates on their own method — rather than compared with itself, which is what `assertThat(V).isEqualTo(V)` was doing. **Found a P5 break in the process:** `inputSchema()` is built from `Map.of`, whose iteration order follows the JVM hash seed, so `tools/list` serialized differently from one boot to the next — unstable bytes on the one payload re-sent every turn, defeating client and prompt-cache reuse. `ShMcpServer` now canonicalizes schema key order, and a test asserts byte stability. → IMPROVEMENTS §VIII.11.
- **SH131** — **the full-text bind contract moved inside the repository** ([ShPostUnifiedRepository](../shio-app/src/main/java/com/viglet/shio/persistence/repository/post/ShPostUnifiedRepository.java)). `FULLTEXT_PREDICATE` needed its `:q` pre-lowercased and `%`-wrapped and said so only in a comment; SH83 read the comment, wrote the caller, and still got it wrong — and the symptom was an *empty result set*, which reads as "nothing matched" and therefore survives review and manual testing alike. The raw `@Query` methods are now suffixed `…Like` (the parameter name says what it wants) and every caller goes through `search*` default methods that normalize exactly once. A contract that can only be honoured by remembering, and whose breach looks like valid data, belongs inside the method rather than beside it. → IMPROVEMENTS §VIII.11.
- **SH132** — **the MCP tool list is a measured budget** ([ShMcpToolBudgetTest](../shio-app/src/test/java/com/viglet/shio/api/agent/mcp/ShMcpToolBudgetTest.java) + `src/test/resources/token-budgets.properties`). The 12-tool cap is a *proxy*; what costs money is the serialized size of `tools/list`, re-sent on every turn of every session before any work happens — eight tools with essay-length descriptions are worse than twelve terse ones and a count test cannot tell the difference (P3). Ceilings live in a properties file with a note on what each guards, so raising one is a reviewable diff with a reason attached rather than an edited magic number; **SH113 extends the same file** with the REST response budgets. - **SH129** — **`shio apply [file]`** ([cli/src/commands/apply.mjs](../cli/src/commands/apply.mjs)), with `--dry-run`, `--check` and `-` for stdin. Law P1's order is MCP → files/CLI → REST, and SH82's content verbs had landed at MCP and REST but not the CLI, so a JS developer with a content document had to `curl` it — which also meant losing the SH80 teaching errors to a wall of raw JSON. `--check` is a plan by definition (a drift guard that could write would not be a guard) and exits non-zero when anything would change, printing *what* drifted so CI is actionable — the same green light `shio push --check` gives for post-types (SH65), now over content. Stdin support is what lets a document be generated by the step before it. This is still a command over a JSON blob, which is a worse authoring surface than a directory; SH87's `shio push --content` is the ergonomic form and will run on this same plan/apply engine once SH86's projection lands, and the command's own header says so. 11 tests ([cli/test/apply.test.mjs](../cli/test/apply.test.mjs)). → IMPROVEMENTS §VIII.7.
- **SH84 (the SH22 half)** — **the tenant sweep over the agent surface** ([ShAgentTenantIsolationIT](../shio-app/src/test/java/com/viglet/shio/tenant/ShAgentTenantIsolationIT.java)). Storage isolation was already proven by `ShTenantIsolationIT`; the agent surface needed its own proof because it resolves content by **address** rather than by id and its purpose is to hand over a complete picture of an instance in one call — a context pack carrying another tenant's sitemap would look exactly like a working context pack. Tenant `beta` gets nothing from the pack, `find` (including full-text), `read`, the address resolver (**including the `id:` escape hatch**), the batch engine or desired-state plan/apply, each failing *absent* rather than *forbidden* per the SH2 rule; and alpha's content survives every attempt. Each expected failure runs in its own transaction, because a failed `@Transactional` call marks the current one rollback-only and the remaining assertions would never execute. **The Turing wiring half of SH84 stays open.** → IMPROVEMENTS §VIII.9.

- **SH77** — **Context pack** (`GET /api/v2/agent/context`). The one call that replaces a session of exploration (design law P2): content **model** (post-types with fields, reusing the SH11 `ShCdaSchemaField` shape so an agent learns one field shape across the product), **sitemap** as a flat depth-first row list keyed by path, derived **conventions**, a **digest**, and a **budget** report. Composition, not a new contract (P10): the model comes from the existing `ShCdaMapper` and site visibility reuses the SH2 per-site token allow-list, so the pack can never show content the CDA would hide from the same credential. [ShAgentContextService](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAgentContextService.java) + [ShAgentContext](../shio-app/src/main/java/com/viglet/shio/api/agent/dto/ShAgentContext.java) (one document type, nested records) + [ShAgentContextSection](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAgentContextSection.java) + [ShAgentProperties](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAgentProperties.java) (`shio.agent.context.*`: default/max budget, default depth, max nodes). Every parameter is optional — the single-site case is a bare GET. **Determinism is load-bearing, not cosmetic:** the `digest` (SHA-256 over the canonical terse body, `c:` + 12 hex) is what lets an agent skip re-reading, so every collection is explicitly sorted (types by name, sites by name, folders by position→name→id, posts by title→id) and the digest deliberately **excludes** the budget/measurement lines so it tracks content only and is identical for the JSON and terse renderings. Folder posts are deduped **draft-preferred**, matching the CDA's `/list`, so the two views of a folder never disagree. **Honest truncation:** only the sitemap is budget-gated (a partial model is not a smaller answer, it is a wrong one — an agent that sees 6 of 9 types invents the other three), cuts are reported with a resumable `from=` cursor, and `truncated` with a `null` cursor is the explicit "nothing fit, raise the budget" signal. Conventions are **derived from the instance** (managed/system type counts, unused types, the DRAFT-then-publish rule, path addressing, multi-site hint) — author-written conventions arrive with SH114. Two new grouped count queries on `ShPostUnifiedRepository` count `distinct p.id` (the unified model stores up to two rows per post) — see the SH22 note below. 21 tests ([ShAgentContextTest](../shio-app/src/test/java/com/viglet/shio/api/agent/ShAgentContextTest.java)). Concept: [specs/SH74-agent-native-cms.md](specs/SH74-agent-native-cms.md) §4.3.
- **SH78** — **Token-lean responses.** The mechanics behind law P3. [ShTokenBudget](../shio-app/src/main/java/com/viglet/shio/api/agent/ShTokenBudget.java) (≈4-chars-per-token estimate, `tryAdd` refuses a chunk without charging it so output is always cut at a row boundary, `overBudget` reports a mandatory-section overrun instead of hiding it), [ShTerse](../shio-app/src/main/java/com/viglet/shio/api/agent/ShTerse.java) (`format=terse` line grammar: one quoting rule — quote iff empty or containing a space/quote — with absent attributes and zero counts omitted entirely), [ShAgentContextTerse](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAgentContextTerse.java) (also the canonical digest input, so what is measured is exactly what is emitted), `include=` section projection with a teaching 400 on an unknown section, and [ShAgentTokenHeaderFilter](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAgentTokenHeaderFilter.java) stamping `X-Shio-Est-Tokens` on every `/api/v2/agent/*` response (measured on the serialized body, so it covers both encodings and cannot drift). **Three findings, each now a test:** (1) *the terse win is per-row, not per-payload* — JSON pays for braces and every key name on every row while terse states the shape once in the verb, so the saving scales with row count (~25–35% per row) and is diluted on a small pack by fixed prose; the assertion therefore measures the **marginal** cost of a row, which is what would catch a node row being "enriched" back into a blob. (2) The residual per-row cost is dominated by the **36-char UUID**, not by the encoding — which makes **SH79 path addressing the larger token lever**, now quantified rather than assumed (→ new SH121). (3) Agent JSON was itself paying for `"folders":0,"posts":0` and four explicit `null`s on every row; `@JsonInclude(NON_DEFAULT)` on the agent DTOs applies the same "don't pay for what you don't say" rule to JSON, so the comparison is against a lean alternative rather than a rigged one (→ new SH125 to make it policy). **Two bugs the tests caught in the implementation itself:** an unbounded budget short-circuited `tryAdd` *without charging*, so `estTokens`/`X-Shio-Est-Tokens` silently under-reported the entire sitemap on every `budget=0` call; and conventions were charged **after** the sitemap gate opened, letting the walk admit rows that the later charge pushed over the ceiling the caller had asked for. Both fixed with regression tests. A misleading `omittedNodes` count was **removed** rather than fixed — the walk stops at the budget so it cannot know how much remains, and the only number it had ("1 more") understated the truth; the scale of what is left is already derivable from the `folders`/`posts` counts on each emitted folder row. 9 tests ([ShTerseAndBudgetTest](../shio-app/src/test/java/com/viglet/shio/api/agent/ShTerseAndBudgetTest.java)) + the SH77 suite. **Scope note:** per-field `fields=` projection on *content* reads is **not** in this task — there are no content reads on the agent surface until SH79/SH83, so it is tracked as SH123. Concept: [specs/SH74-agent-native-cms.md](specs/SH74-agent-native-cms.md) §4.4.
- **SH79** — **Path addressing.** A content address — `post:<site>/<friendly-url>`, `folder:<site>/<name-chain>`, `site:<name>`, `id:<uuid>` — so a UUID stops being the agent's working currency (design law P5). [ShAddress](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAddress.java) (parse/normalize/canonical form) + [ShAddressResolver](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAddressResolver.java) + `GET /api/v2/agent/resolve?address=…` → [ShAgentResolved](../shio-app/src/main/java/com/viglet/shio/api/agent/dto/ShAgentResolved.java), plus `shio resolve <address>` (`--id` for pipelines) and `site=` on the context pack now accepting a `site:` address. **The shape decision that kept this from being a token regression:** the obvious reading of "path addressing" is to emit an `address` on every context row — but a row already carries its site, path and url, so a built address duplicates derivable information and *adds* tokens to the very endpoint this task was supposed to make cheaper. Instead the grammar is stated **once**, as a convention line, and the resolver makes those addresses actionable; a test asserts no row carries an `address=` attribute. The token win itself lands in SH121, which removes the id. **Two namespaces are kept deliberately apart:** a folder path is a chain of folder *names*, while a post's `furl` is arbitrary and need not relate to its folder — so the scheme names which is meant, and the lenient `site:` form (post-first, then folder) raises a **400 naming both explicit addresses** when a path is occupied by both rather than silently picking one. That case is real and is in the fixture: a post whose `furl` is `/blog` alongside a `/blog` folder. Resolution reuses the CDA's own furl candidates (so an address and a delivery URL never disagree about the same post), is draft-preferred like `/list`, honors the SH2 allow-list, and reports a disallowed site as **absent rather than forbidden** — a scoped key must not be able to use a 403 to prove a site exists. `addressOf(…)` is the inverse, tested as a round trip because SH121 depends on it. Failures teach: a malformed address returns the schemes and a corrected example; an unresolved one lists the sibling paths with a nearest match (`/blg` → `/blog`). Known limit, documented: a site whose *name* contains `/` must be addressed by id. 22 new backend tests + 6 CLI; suites 360 and 39 green. → §VIII.5

- **SH125** — **Null/default omission as policy, with the counter-rule.** Nulls are always waste (`"url": null` and an absent `url` say the same thing), so every agent-owned DTO omits them — enforced by [ShAgentJsonLeanTest](../shio-app/src/test/java/com/viglet/shio/api/agent/ShAgentJsonLeanTest.java), which serializes real responses and fails on any `:null`. **The interesting half is what the policy refuses to do.** A blanket `NON_DEFAULT` — the obvious "make it smaller" move, and what the task originally proposed — would have stripped the `false` entries from the manifest's `features` map and `truncated: false` from a budget report. - **SH168** — **A write refuses a field the post-type does not declare** ([ShAgentBatchService](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAgentBatchService.java), [ShAgentVerifyService](../shio-app/src/main/java/com/viglet/shio/api/agent/verify/ShAgentVerifyService.java)). `post.upsert` stored any key handed to it, and because an upsert declares *whole state* a mistyped field name did not add a key — it **replaced** the one that was meant with one nothing reads. - **SH171** — **A multi-address read fails per row, not per call** ([ShAgentReadService](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAgentReadService.java), [ShAgentDoc](../shio-app/src/main/java/com/viglet/shio/api/agent/dto/ShAgentDoc.java)). `GET /agent/read` with N addresses 404'd the whole call when any one was unresolvable, which inverted the saving the batch form exists for: the agent then re-read the addresses one at a time to find the offender. Now each row comes back positionally — the SH80 slug, title and fix in place of its content — and the **single**-address form still 404s, because callers depend on that.
  <br>**One transactional subtlety made it real.** Catching a teaching exception inside `@Transactional(readOnly = true)` is not enough: the inner interceptor had already marked the shared transaction rollback-only, so the successful rows blew up at commit with `UnexpectedRollbackException`. `noRollbackFor = ShTeachingException.class` on the resolver and the read service fixes it, and is safe precisely because both are read-only lookups — an enclosing *write* transaction has no such exemption, so a batch op that cannot resolve still rolls the whole batch back.
- **SH172** — **An address names one post, or it is an id** ([ShAddressResolver](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAddressResolver.java)). A post with no friendly URL has no address under SH79's scheme, and `find` rendered it as `post:<site>/` anyway — so three URL-less `File` posts came back as three rows carrying the *same* address, none of them actionable, none of them saying anything was wrong. SH100's lint had already answered this correctly by falling back to `id:<uuid>`; the two surfaces disagreeing was the defect. The fallback now lives in `addressOf`, the one place both of them ask, so `find`, `changes`, the change rows and the review queue agree by construction — the invariant is enforced rather than restated (§VIII.10's rule). A site-less post (the SH128 class) falls back for the same reason.
  <br>The response says so once, at the top (`notes`), rather than marking every row: a File-heavy site would otherwise pay for the same sentence on every row, and the `id:` prefix is already visible where it applies.
- **SH175** — **A conditional requirement is stated on the argument** (`shio_write`'s schema). `type` said it was needed only when creating; `folder`, needed on exactly the same op, described itself as a hint — so the most common write on the surface, an agent's first create, paid a round trip to learn it from the error. The schema is the one document a model reads *before* calling. Deliberately a sentence rather than JSON Schema's `if`/`then`: a conditional keyword an MCP client may or may not surface is a worse deal than a description the model definitely reads.

## Block K — Perception & verification loop (SH74)

> The block removes the *first* of the three human round trips in a typical build: the
> one that exists only because the agent cannot check its own work. Everything here is
> answered from state the instance already holds — no rendering, no crawling, no browser
> — because the cheap textual proof is the one that gets run.

- **SH99** — **Content lint** (`GET /api/v2/agent/verify`, `shio verify`, `shio_verify`). The content-side `tsc`: [ShAgentVerifyService](../shio-app/src/main/java/com/viglet/shio/api/agent/verify/ShAgentVerifyService.java) walks the readable content once and reports `required-field-empty`, `dangling-reference`, `missing-asset`, `unpublished-dependency`, `duplicate-url`, `orphan-post`, `orphan-folder` and `empty-folder` as [ShAgentReport](../shio-app/src/main/java/com/viglet/shio/api/agent/verify/dto/ShAgentReport.java) findings, each with an SH79 address and an SH80-style `fix`. The design calls: (1) **`ok` tracks errors, never warnings** — an error is broken from a visitor's point of view, a warning is something the CMS cannot prove from inside itself (an empty folder may be a section under construction), and an exit code that failed on the second kind is an exit code that gets wrapped in `|| true`; (2) **truncation is never silent** — `found` counts the whole run while `findings` carries what fitted, the same hazard SH138 records for deletion plans; (3) **a cross-site reference is not called dangling** — a target the credential cannot read is re-checked by id first, so the allow-list never manufactures a defect; (4) **one read pass, both states** — the duplicate-URL rule is only meaningful between `PUBLISHED` rows and "published depends on unpublished" cannot be asked without knowing which ids have one. A new repository finder, `findWithoutSite`, exists solely so the lint can see the **SH128 defect class** — a site-less post is invisible to every other finder by construction, and a lint blind to the defect its own guard was written for is not much of a lint. Ships the **ninth MCP tool**: `shio_verify` was held back from SH83 for want of something real to verify, and this flips the manifest's `contentLint` from the `false` it reported through all of Block H. 15 tests ([ShAgentVerifyTest](../shio-app/src/test/java/com/viglet/shio/api/agent/verify/ShAgentVerifyTest.java)) build every defect through the SH81 batch surface, so the rules are proved against content an agent could actually have written. → was §IX.1
- **SH100** — **Route/link verification**, as the `routes` check group of the same report: `url-missing` on a published post with no friendly URL, `link-unresolved` for a site-relative href matching no published URL, `asset-missing` for a `/file_source/<id>/<name>` with no bytes on disk, and `image-no-alt`. **It does not crawl.** "Internal links return 200" is answered against the content graph — the set of published furls, compared through `ShAddress.normalizePath` (made public here so there is exactly one canonical path form in the instance, P5) — rather than by fetching a front end that may not be running, may be a different deployment, and legitimately owns routes the CMS has never heard of. That last point is also why `link-unresolved` is a **warning**: on any real site the front end owns generated routes, and reporting those as errors would make the gate useless. Only `PUBLISHED` rows are route-checked (a draft's broken link is work in progress) and only the two markup widgets are scanned (a plain Text field holding something path-shaped is not a link). → was §IX.2
- **SH101** — **Render digest** (`GET /api/v2/agent/render`, `shio digest`, `shio_digest`). [ShHtmlOutline](../shio-app/src/main/java/com/viglet/shio/api/agent/verify/ShHtmlOutline.java) scans markup into a heading outline, landmark counts, a link inventory and an image inventory **with alt text**, plus a word count; [ShAgentRenderService](../shio-app/src/main/java/com/viglet/shio/api/agent/verify/ShAgentRenderService.java) shapes it into [ShAgentDigest](../shio-app/src/main/java/com/viglet/shio/api/agent/verify/dto/ShAgentDigest.java). Four calls worth naming: (1) **two sources** — `address=` digests the markup Shio holds (no front end needed, usable immediately after a write) and `url=` digests what a visitor actually gets; (2) **fetching is off by default** (`shio.agent.render.allow-fetch`) and restricted to the origins of *readable* sites, because an endpoint that fetches an arbitrary URL on the server's behalf is a request forgery with a friendly name — and the origin check keeps the agent path from being a privilege escalation, the Block L invariant; (3) **the `digest` hash covers structure only** — heading levels and text, landmark counts, link hrefs, image sources and whether each has alt — so a typo fix does not move it and a lost heading does, which is what makes "did this page change shape?" a string comparison instead of a re-read; (4) **a missing `alt` attribute and `alt=""` are kept apart**, because the second is how decorative markup is *correctly* declared and collapsing them would train the agent to "fix" it. A scanner rather than an HTML parser, with the trade stated in the class doc: a digest is not a DOM, and the failure mode of a scanner is a slightly wrong outline, never invented structure. `visualSnapshot` (SH102) is reported `false` on purpose — a PNG costs orders of magnitude more tokens and tells the agent less. 10 tests ([ShAgentRenderTest](../shio-app/src/test/java/com/viglet/shio/api/agent/verify/ShAgentRenderTest.java)). → was §IX.3
- **SH103** — **Agent diagnostics** (`GET /api/v2/agent/diagnostics`). The asynchronous half of the loop: SH80's teaching errors answer the call that failed, this answers the failures that happen *after* the agent moves on. [ShAgentIncidentLog](../shio-app/src/main/java/com/viglet/shio/api/agent/diagnostics/ShAgentIncidentLog.java) is a bounded in-memory ring buffer wired into the four places that previously only logged a warning: the webhook dispatcher (a delivery that never arrived is the difference between *published* and *visible*), the Thumbnailator pipeline (a failed transform serves the original and surfaces nothing), the publish scheduler (nobody is watching at 03:00), and a new `ShAgentErrorRecordingFilter` for 5xx — a filter rather than a catch-all `@ExceptionHandler`, so no existing client's error body changes, and registered outside the security chain so a rejected scan is not recorded as an instance fault. Two properties do the real work: **repeats fold** into one row with a count (one broken webhook retried on every publish would otherwise evict every other incident from a 50-slot window — the one way a diagnostics log actively misleads), and the response **states its own bound** via `since`/`dropped`/`notes`, because "no incidents" otherwise reads as a clean bill of health when it may mean "nothing is remembered". A disabled webhook subsystem says so explicitly, for the same reason. The incidents also surface as `diagnostics`-group findings in the verify report, since an agent that has to remember a second call will not make it. 6 tests ([ShAgentDiagnosticsTest](../shio-app/src/test/java/com/viglet/shio/api/agent/diagnostics/ShAgentDiagnosticsTest.java)). → was §IX.5
- **Block K wiring** — manifest: `contentLint` flips to `true` (backed by real rules, not a stub that always passes) alongside new `routeCheck`, `renderDigest`, `diagnostics` and the configured `renderFetch`; three endpoints join the curated index and `startHere` gains the verify step (the existing five-line cap held by folding the digest hint into the context line). CLI: `shio verify` (`--site`/`--checks`/`--limit`/`--strict`, **exit 1 on an error** so it sits in CI beside `shio push --check` and `shio apply --check`) and `shio digest <address|url>`, with 10 network-free tests ([verify.test.mjs](../cli/test/verify.test.mjs)). Terse renderings for all three payloads ([ShAgentVerifyTerse](../shio-app/src/main/java/com/viglet/shio/api/agent/verify/ShAgentVerifyTerse.java)) — a report is the worst possible shape for JSON, and unlike a listing it is read in full by definition, so the saving is never wasted. The SH132 tool-list budget rises 1750 → 2110 for the two new tools (~355 est. tokens per turn), which is the trade the whole block exists to make: a fixed per-turn cost against a human round trip that costs orders of magnitude more.

## Block I — Content as files (SH74)

> The block removes the *second* human round trip: authoring over HTTP. Content projects
> to a git-diffable text tree, the tree syncs both ways, and the merge is three-way — so
> a human curating in the console and an agent writing files are both first-class writers
> rather than one overwriting the other.

- **SH88** — **Change feed with a cursor** (`GET /api/v2/agent/changes`, `shio changes`, `since=` on `shio_changes`). [ShAgentChangesService](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAgentChangesService.java) + [ShAgentChanges](../shio-app/src/main/java/com/viglet/shio/api/agent/dto/ShAgentChanges.java) + [ShAgentChangeCursor](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAgentChangeCursor.java), with keyset queries on `ShHistoryRepository`. **The cursor is `(instant, id)`, not a timestamp** — the reason SH83 shipped a window and refused to fake one: audit rows share timestamps (a batch of twelve writes commits inside one second, and on a MariaDB with second-precision columns inside one *value*), so a timestamp cursor either re-delivers a whole second or silently drops the entries that tie. A cursor with no `|<id>` part is a **teaching 400** rather than an interpretation, because the failure it would cause is invisible. **Both modes share one order** (oldest → newest), so the cursor is always the last row and a caller never has to know which mode it got; an empty read returns the position it was given, and an empty *window* returns a synthetic anchor (`<ceiling>|`), so a quiet instance still yields a place to stand. **The lag rule:** SH51 writes the audit row inside the writer's transaction, so its timestamp is assigned *before* the commit and a slow transaction can land an older timestamp behind a cursor that already passed it — the feed therefore refuses to report anything younger than `now - shio.agent.changes.lag-millis` (1s default). That narrows the window rather than closing it, and the response says so in `notes` instead of implying exactness; the real fix is **SH147**. **A leak closed on the way:** `shio_changes` read the whole trail through `findRecent`, ignoring the SH2 per-site allow-list, so a scoped token could see the titles of content it could not fetch — both surfaces now route through this service, which scopes to readable sites (and keeps unattributable rows for unrestricted credentials only). Rows carry an SH79 address, resolved once per object and absent when the object is gone (the normal state of a `DELETE` row, whose title travels in `what`). Flips the manifest's `changeCursor`, which was reported `false` through Blocks H and K on purpose. 11 tests ([ShAgentChangesTest](../shio-app/src/test/java/com/viglet/shio/api/agent/ShAgentChangesTest.java)). → was §X.3
- **SH86** — **The filesystem projection format** ([cli/src/content-files.mjs](../cli/src/content-files.mjs)): one post, one `shio/content/<site>/<url>.md` — YAML frontmatter for the metadata and fields, the post's rich-text field as the document body. Pure and unit-tested, in the shape `post-types-io.mjs` established. The four design questions the roadmap left open, answered: (1) **the path is the friendly URL, not the folder chain** — a URL is unique per site by definition so the tree cannot collide, and the folder travels in frontmatter because SH79 is explicit that the two are separate namespaces and deriving one from the other would place content in the wrong folder silently; (2) **only the DRAFT projects**, and `publish:` in a file is an *instruction* a push forwards rather than state a pull writes back (P7 — a tree holding both copies would make "what does the site show?" a question about which file you opened); (3) **`fields:` is nested** under its own key, because a post-type may legitimately have a field called `type` or `url` and a flat map would let content overwrite the document's identity; (4) **anything that is not a scalar or a list of scalars stays compact JSON** — a YAML rendering of arbitrary nesting is a second serialization format to specify and get wrong, and the write side already speaks JSON. **Losslessness is absolute, and the format gives up prettiness to keep it:** a value that would not survive the round trip (leading/trailing whitespace, an empty string, a body that is not exactly its own trim) stays in `fields:` as a JSON string instead of becoming the body, and the one normalization — a body's CRLF becomes LF — exists precisely so a pull cannot report a change nobody made. The body field is chosen as the first `HTML Editor` field by ordinal and **written into the file** as `body:`, so reading a projection back never consults the model; a `Text Area` is deliberately never promoted, since a rule that guessed at the "main" text field would move content between fields the moment someone added one. A hand-written file takes its `site`/`url` from its path (law P4: `Write` should not require ceremony), and a path that *disagrees* with the frontmatter is refused rather than guessed — a rename on one side only is a move on one side and a create on the other, which is SH134's lesson arriving on the file side. 13 tests ([content-files.test.mjs](../cli/test/content-files.test.mjs)). → was §X.1
- **SH87** — **Two-way content sync**: `shio pull --content` and `shio push --content` ([content-pull.mjs](../cli/src/commands/content-pull.mjs), [content-push.mjs](../cli/src/commands/content-push.mjs), [content-store.mjs](../cli/src/content-store.mjs)) — the same two verbs the model already had, over the other resource, so an agent that learned pull/push does not learn a second vocabulary for pages. Push compiles the tree into one desired-state document per site and applies it through `POST /agent/plan`/`/apply` (P10 — no third write path, so atomicity, teaching errors and prune rules are the ones already tested), which makes `--check` the content-tree drift guard beside `shio push --check` (SH65) and `shio apply --check` (SH129). Folders are declared from the posts' own `folder` values **plus every ancestor**, because a document declaring `/blog/2026` without `/blog` would put a whole level outside its own prune scope. **Two refusals worth naming, both of the same family as SH138:** a **truncated** `find` result means the projection would omit posts, and the very next `push --prune` would read those gaps as deletions — so pull refuses to write a partial projection unless `--allow-partial`, and the snapshot it then writes stays marked `partial` so a later prune refuses too (the cap itself is **SH146**); and `push --content` on an empty content directory is an error, because "no files" plus `--prune` is a request to delete a section and is far more often a wrong `--content-dir`. 13 command tests ([content-commands.test.mjs](../cli/test/content-commands.test.mjs)). → was §X.2
- **SH89** — **Conflict policy: a three-way merge, per field** ([content-sync.mjs](../cli/src/content-sync.mjs)). A sync with only "mine" and "theirs" has to pick one, and picking is a clobber; both actors here are legitimate writers, so the engine keeps the **base** — what the two sides last agreed on — in `shio/.shio/content-base.json` along with the SH88 cursor. One side changing takes that side; different fields changing on each side **merge**; the same field changing on both is a conflict named by field (`fields.headline`). **Metadata merges by the same rule**, so a post moved in the console and rewritten in a file is not a conflict. **No conflict markers, ever:** `<<<<<<<` in a field value is *content*, and the next push would send it to the server and the next publish would put it on the site — so a conflict writes nothing for that post, is reported with a non-zero exit, and `--show-remote` drops the server's copy beside the file as `<file>.remote` so a diff is still one command away; `--ours`/`--theirs` resolve deliberately. **The rule that makes push safe** is the one that is easy to get wrong: a post the tree did *not* change but the server *did* is declared with the **server's own values** — declaring the base would quietly revert a console edit, and omitting the post would drop it out of the declared set where `--prune` would delete it. A deletion on either side is never silently undone: server-deleted plus untouched file deletes the file, file-deleted plus untouched server stays deleted and waits for `--prune`, and deleted-on-one-side-edited-on-the-other is a conflict. 15 engine tests ([content-sync.test.mjs](../cli/test/content-sync.test.mjs)). → was §X.4
- **SH90** — **`shio dev --content`** ([content-watch.mjs](../cli/src/commands/content-watch.mjs)): a file watcher on the content tree plus a poll of the SH88 feed, both funnelling into one `syncOnce` that **pulls before it pushes** — bringing the server's edits down first is what makes a simultaneous edit *visible* instead of overwritten, and a conflict stops the push for that run rather than leaving the tree and the instance in a state neither side asked for. Bursts coalesce (one sync per burst, one rerun if a trigger arrives mid-run) and the loop returns a stoppable handle instead of blocking, which is also what lets it be tested with no clock. The record is **JSONL** at `shio/.shio/dev-events.jsonl` — one object per event with its kind, counts and timestamp — because a failure buried in a long scrollback costs the agent a reconstruction, while `grep` over one-object-per-line answers "did anything conflict while I was working?" directly. Human-readable lines still go to stdout; losing the log never stops the sync it describes. `shio dev` without `--content` is unchanged, and `--content` deliberately does *not* spawn the site's dev server (a content repo has no `run dev` script to spawn). → was §X.5
- **Block I wiring** — manifest: `contentAsFiles` and `changeCursor` both flip to `true` (each was `false` through two blocks so that flipping it would mean something), and `/agent/changes` joins the curated endpoint index. CLI: `shio changes` (`--since`, `--since last` reading the last pull's position, `--cursor` for `SINCE=$(shio changes --cursor)`, `--site`, `--limit`, `--json`) and `--content` on `pull`/`push`/`dev`. Terse rendering for the feed ([ShAgentChangesTerse](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAgentChangesTerse.java)) puts the cursor on the **header** line, since it is the one value the caller must carry forward and burying it after fifty rows would end the cheapest read on the surface with a search. `shio_changes` gains `since` without adding a tool, so the SH132 tool-list budget is unchanged; the SH130 golden was regenerated and the diff is exactly the new parameter. **A pre-existing test fragility fixed rather than worked around:** `ShAgentContextTest`'s "budget that cuts the sitemap" was three quarters of the whole pack, but the mandatory sections are charged first and the **model is instance-wide**, so any new test class that adds a post-type pushed them past the cut and starved the sitemap of every row — the helper now measures the sitemap's own cost, so the cut lands where the test means it whatever else the shared database holds.

### Block J follow-ups — a package can create the site it needs, and reconcile a model it does not own

- **SH151** — **A blueprint apply can create its target site** (`createSite` on [ShBlueprintRequest](../shio-app/src/main/java/com/viglet/shio/blueprint/dto/ShBlueprintRequest.java), [ShSiteWriteService#createBlank](../shio-app/src/main/java/com/viglet/shio/api/site/ShSiteWriteService.java), `shio apply --create-site`). *"One call builds a marketing site"* was one call only if a site already existed to apply it into, and the only creation path cloned the SH71 bootstrap template — so "create a site for this package" meant applying a package on top of a Welcome page nobody asked for and then pruning it. Hence a **blank** site path, which is worth having on its own: the clone exists because an empty site used to be useless, and a blueprint is exactly the thing that makes it useful.
  <br>**The default stays a refusal.** Creating a site is the most visible side effect in the system, so it is requested, never inferred from "the site you named does not exist" (P7). What changed is that the refusal now *names both routes* — the flag, and a `site.upsert` op — instead of pointing at `POST /api/v2/site`.
  <br>**A plan creates it inside the transaction it rolls back**, the same technique the post-type half already uses and for the same reason: without the site, the content planner cannot resolve a single address, so a plan for a not-yet-existing site could not be a plan at all. Nothing survives the return, and the test asserts that.
- **SH152** — **Additive post-type reconciliation** (`mergePostTypes`, [ShPostTypeAdminService#mergeMissingFields](../shio-app/src/main/java/com/viglet/shio/api/post/type/ShPostTypeAdminService.java), [ShPostTypeMergeTest](../shio-app/src/test/java/com/viglet/shio/api/post/type/ShPostTypeMergeTest.java)). A package's post-type that already exists was left alone and its missing fields *reported* — honest, and one step short of useful. **SH168 made it worse than that**: those content writes are now refused rather than silently mangled, so the report named a wall instead of a wart. The opt-in merge adds the fields the package declares and the type lacks, and nothing else: never changes a widget or its settings, never removes a field, never reorders, never touches a system type. Every one of those exclusions is something somebody else may own.
  <br>**Two decisions, both visible in the tests.** An added field's **ordinal is appended** after the highest existing one — honouring the package's own ordinals would push a human's field down their form. And the report says **`merge`** with the fields it `added`, because a merge that read as a provision would hide that the type is now a hybrid of two models, which is exactly what somebody debugging the form six months later needs to know.
- **SH170** — **`site.upsert`: the batch surface can make a site** ([ShAgentBatchService](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAgentBatchService.java)). Seven ops could build everything inside a site and none could make one, so an agent asked for the thing the product is *for* found that step one was not here — and landed on the console entity API: id-keyed, entity-shaped and CSRF-gated, which answers a stateless caller with a bodiless 403. Nothing to read, nothing to fix. The eighth op is addressed (`site:<name>`), idempotent, and creates a **blank** site.
  <br>**It never updates**, deliberately: the name is the address, and a site's URL, description and layout are console concerns with a human looking at them. An "upsert" that quietly repointed a live site's URL because a document mentioned it would be the surprise P7 forbids — so it creates or reports `noop`, and says which. **It refuses a scoped credential**: a token with an SH2 site allow-list may not invent a site outside it, which would make the allow-list "sites this token may read, plus any it makes up".
  <br>**Not on the MCP tool schema, and that is the interesting part.** `createSite` on `shio_apply` measured 18 tokens over the per-tool ceiling and pushed `tools/list` over its total — a bill every session pays on every turn, including the ones that never create a site (P3). It is not needed there: `shio_write` takes `site.upsert` for free, because it is one more value in an `op` enum that already existed, and the missing-site error names it. The manifest advertises `siteUpsert` so nobody has to discover it by reading the Java.

### Block K follow-ups — the third report state, and a run scoped to what changed

- **SH142** — **Accepted findings** ([verify-baseline.mjs](../cli/src/verify-baseline.mjs), [commands/verify.mjs](../cli/src/commands/verify.mjs)). A report had two states and real content has three. `ok`/`not ok` cannot say *known and accepted* — a decorative image the markup cannot describe, a folder deliberately staged empty, a link into a route the front end owns — and the first legitimate warning nobody intends to fix is the moment the exit code stops being read. After that the errors go unread with it. A committed `shio/verify-baseline.json` of `(rule, address, field)` triples is subtracted before the gate decides.
  <br>**The half that keeps it from becoming a blanket suppression:** an accepted finding that the run *no longer produces* fails the run. Without it an entry outlives the defect it excused and silently swallows the next real one at the same address — which would make the file worse than not having it. That check is also why an entry is a triple and not a rule name. Matching is on rule + address + field, deliberately not on `message` (a copy-edit would look like a new defect) and not on `severity` (promoting a rule would quietly un-accept everything).
  <br>**A truncated report cannot prove staleness**, so it does not try: an unmatched entry is reported and the run does not fail on it, because a finding that did not fit is not a finding that is gone — the SH138 hazard read from the other side. `--accept` writes the baseline (naming every entry on stdout, `--reason` optional) and **merges** rather than replaces, since a run narrowed by `--site` sees only part of the project. It accepts errors as well as warnings on purpose: SH168's `unknown-field` is exactly the class that otherwise sends people to `|| true`.
  <br>**Deliberately a project file and not an instance setting.** What is acceptable is a property of *this repository's* content and belongs in review beside it, and the thing it protects — the exit code — is the CLI's. `GET /agent/verify` keeps reporting every finding, which is right: an agent asking "what is wrong here" should be told, including about the parts a human already signed off. Only the gate subtracts. 15 network-free tests ([verify-baseline.test.mjs](../cli/test/verify-baseline.test.mjs)).

- **SH143** — **A verify run scoped to what changed** ([ShAgentVerifyScope](../shio-app/src/main/java/com/viglet/shio/api/agent/verify/ShAgentVerifyScope.java), [ShAgentVerifyService](../shio-app/src/main/java/com/viglet/shio/api/agent/verify/ShAgentVerifyService.java)). The pass read every post in every readable site — right for CI, and roughly a hundred times more work than the call an agent makes after writing three pages. `?folder=` (a subtree), `?address=` (named posts, comma-separated) and `?since=` (an SH88 cursor) narrow it; the three **union** rather than intersect, because each names something the caller wants looked at. Also `shio verify --folder/--address/--since` and three arguments on `shio_verify`, which is the caller this was built for.
  <br>**Why it is a refactor and not a filter.** Two rules ask cross-cutting questions — is another published post claiming this URL, does this link land anywhere in the site — and one asks whether a folder holds content. A scoped run that answered any of them from its own subjects would invent defects that are not there (`link-unresolved` for every link out of the scope, `empty-folder` for every folder it did not look inside) and miss the one that is: a duplicate whose twin is outside. So the **subjects** narrow and the **indexes stay whole**, built from id/url/state projections — one query per site, no entities, none of the cost a full read pass is expensive for ([findUrlIndexBySiteId](../shio-app/src/main/java/com/viglet/shio/persistence/repository/post/ShPostUnifiedRepository.java), `findFolderIdsWithPosts`, [findParentFolderIds](../shio-app/src/main/java/com/viglet/shio/persistence/repository/folder/ShFolderRepository.java)). `duplicate-url` became a per-subject lookup against the index for the same reason, and on a full pass emits exactly what it always did.
  <br>**A subset never reads as a full pass.** A scoped run sets `partial` and describes itself in `scope` (both absent on a full run — a flag that is always present is a flag nobody reads), the terse header carries them, and a `since` feed with more entries than fitted is a `note` rather than a silent cut. A `folder=` that resolves to something that is not a folder is a teaching **400**, not an empty green run: a scope that covered nothing while answering `ok` is the most dangerous false green there is. 9 tests, three of them about what scoping must not break ([ShAgentVerifyScopeTest](../shio-app/src/test/java/com/viglet/shio/api/agent/verify/ShAgentVerifyScopeTest.java)).
  <br>**Budget:** `mcp.tools.list.total` 2160 → 2200 — the one raise on that file where the schema cost is repaid inside the same feature, since the arguments exist so the tool can stop returning a whole-instance report. Two rounds of trimming went first.

### Block K follow-ups — a durable record, the route proof, and the handoff a human reads

- **SH144** — **The durable incident feed** ([ShAgentIncident](../shio-app/src/main/java/com/viglet/shio/persistence/model/agent/ShAgentIncident.java), [ShAgentIncidentStore](../shio-app/src/main/java/com/viglet/shio/api/agent/diagnostics/ShAgentIncidentStore.java), [v2026.3.12.yaml](../shio-app/src/main/resources/db/changelog/v2026.3.12.yaml), `incidents` on [ShAgentChanges](../shio-app/src/main/java/com/viglet/shio/api/agent/dto/ShAgentChanges.java)). SH103's window was in memory and said so — which was the right answer for a first pass and an admission: "was anything failing while I was away" is a question about a period a ring buffer may no longer cover, and a restart answered it with silence. Now the record is a table, and one `since=` answers what changed *and* what broke. 11 tests ([ShAgentDurableIncidentTest](../shio-app/src/test/java/com/viglet/shio/api/agent/diagnostics/ShAgentDurableIncidentTest.java)), plus two of SH103's own rewritten because the behaviour they pinned is deliberately gone.
  <br>**Folding is what makes the table affordable.** SH103's objection was a write on the failure path plus a retention policy. A row is keyed by *what went wrong* (`kind`, `subject`, `message`), not by each occurrence, so one broken webhook retried for a month is one row with a count — the table grows with the number of distinct problems, which is a number an operator wants to see anyway. The pathological case (a subject carrying an id) is bounded by `shio.agent.diagnostics.max-rows`, and what the cap drops is visible through `since` moving forward rather than being quietly forgotten.
  <br>**The write cannot make things worse.** It runs in **`REQUIRES_NEW`**, because several callers are inside a transaction that is about to roll back — the 5xx filter's request, a scheduled publish that threw — and a row enlisted in that transaction would be destroyed by the very failure it exists to record. And it **never throws**: anything the persistence layer raises is caught and logged, since a diagnostics store that turned a webhook timeout into a 500 would be strictly worse than forgetting the incident. A failed write is counted, and the payload says the record is incomplete — the case that matters most, because the likeliest reason a write failed is that the database was itself what was failing. The in-memory buffer therefore stays: it is what is left when the store is unavailable.
  <br>**`lastSeen` is the feed position, not `firstSeen`.** A folded row moves *forward* when it recurs, so a cursor never steps over it and an ongoing outage is re-delivered with a higher count. Ordering by first occurrence would have been stable and wrong: a failure that started before your cursor and is still going would be reported once, ever. Two payload fields changed meaning in the same direction — `since` is where the record starts (**absent** when nothing was ever recorded, which is now genuinely "nothing has failed"), and `dropped` is now "could not be written down", the only remaining way an incident is lost.
  <br>**The invariant the merge turns on: an incident may repeat, a change may never be lost.** Two streams paged independently under one scalar cursor cannot both be exactly-once. The obvious move — return the *later* of the two positions — is wrong in the unacceptable direction, and it is not hypothetical: it made SH88's timestamp-tie test fail, because an incident minutes ahead of the audit page being walked advanced the cursor past rows the caller had never seen. So the cursor advances past an incident only when the change stream reports no `more`, meaning the audit has been drained to the ceiling and there is nothing for a later position to skip; until then the cursor stays the audit's and those incidents are simply read again, which costs nothing because rows are folded. There is now a test that pins exactly that.
  <br>**Shaped as its own array, not as a `Change` with an invented `action`.** Every existing caller branches on `action` and would have filed a failure as a content transition — pulling it into a file tree, counting it as work done. A separate array is a field a caller can ignore; a fake action is a field a caller can misread. Same reasoning in the terse rendering (`incident`, its own verb) and in `shio changes` (`!`-marked). Incidents carry **no site**, so a site-scoped read cannot narrow them and the `notes` say so rather than implying otherwise — no new visibility, since `/agent/diagnostics` has been instance-wide since SH103, and attributing them is filed as a follow-up. `shio report` picks them up for free: a webhook the front end never received is exactly a handoff concern, and it now appears in the handoff without a second call. Manifest: `durableIncidents`.

- **SH104** — **The handoff report** ([report.mjs](../cli/src/report.mjs), [commands/report.mjs](../cli/src/commands/report.mjs), `shio report`). Block K removed the human round trip that existed because the agent could not check its own work; this is the other half of the same brief — the one that exists because a human cannot see what the agent *did*. `shio verify` is the agent's output for a machine. This is its output for a person: what changed, a preview link per page, and the questions the CMS cannot settle itself, as Markdown ready for a PR body. 17 network-free tests ([report.test.mjs](../cli/test/report.test.mjs)).
  <br>**It composes three reads and adds no endpoint.** The SH88 feed knows what moved, the SH77 context pack knows each site's public URL, and the SH99 report knows what is unresolved — a `GET /agent/report` would be a fourth contract restating three (P10), and it would put *presentation* on the server, where a Markdown template then has to be versioned alongside the protocol. The pack is fetched as `include=sites` only: one field is needed from nine sections, and a read that pays for the other eight is a token bill nobody asked for (P3). **No MCP tool either** — the artifact's consumer is a human, so per-turn schema would be paid for something the agent hands to someone else, and the agent has a shell (the argument SH114's memory already made).
  <br>**Four rules, all of them about what a summary must not quietly omit.** A **deletion is a first-class row**: it has no address and no link, which makes it the row an implementation that builds the list out of links drops, and the row a reviewer most needs. A **preview link is never invented** — it exists when the site has a URL *and* the post has a friendly URL, and otherwise the report names which half is missing, because a plausible link that 404s costs the reader their trust in the whole document. The **warnings are the open questions** and errors are only *counted*, with the count in the first paragraph: an error is broken and belongs in the agent's loop before a human is asked to look, and restating each one here would create a second copy of the lint report that drifts from the first. And everything that makes the document less than complete — the feed's `more`, its lag note, a truncated or `partial` verify — goes in a **"What this report does not cover"** section *above* the footer, because this is the SH138 hazard at its worst: a shortened list of changes reads exactly like a complete review of a small change set, and the document exists to be trusted *instead of* the diff.
  <br>**A read does not move a cursor.** The report waited on SH88 so it could start where the last one ended, but advancing the position as a side effect of reading means running it twice gives two answers and the second says "nothing changed" — which for a review artifact reads as approval. So `--since last` reads a position and only **`--mark`** writes one, and `--mark` **refuses** when the report carried caveats about its own completeness: a cursor moved past changes nobody saw is a permanent hole in the review trail. That is the same refusal `pull --content` makes about a truncated projection. Losing the context pack degrades to naming why each link is absent rather than to failing — the failure must cost the links, not the document.

### Block K follow-up — the route proof that closes the warning

- **SH141** — **Proving a route from the delivery side** ([ShAgentDeliveryProbe](../shio-app/src/main/java/com/viglet/shio/api/agent/verify/ShAgentDeliveryProbe.java), [ShFrontEndRoutes](../shio-app/src/main/java/com/viglet/shio/api/agent/verify/ShFrontEndRoutes.java), the `delivery` group on [ShAgentCheck](../shio-app/src/main/java/com/viglet/shio/api/agent/verify/ShAgentCheck.java) + [ShAgentVerifyService](../shio-app/src/main/java/com/viglet/shio/api/agent/verify/ShAgentVerifyService.java), `shio verify --delivery`). SH100 answered "internal links resolve" against the content graph, which was the right first move — no front end, no network, runs in a cold CI checkout — and could not see the failure §IX names as the most common one: **a page that exists in the CMS and 404s on the site**. So `link-unresolved` was a warning, because a warning is what you emit when you are not sure. This makes it sure: each published page and each unresolved link is requested from the site's own origin, and a non-2xx becomes `route-not-served` or `link-broken`, both **errors**. 15 tests ([ShAgentDeliveryTest](../shio-app/src/test/java/com/viglet/shio/api/agent/verify/ShAgentDeliveryTest.java) runs a real loopback front end — a mocked fetch cannot reproduce a *disagreement between two systems*, it only fails however the mock was written; [ShFrontEndRoutesTest](../shio-app/src/test/java/com/viglet/shio/api/agent/verify/ShFrontEndRoutesTest.java)).
  <br>**It is not a crawler, and the difference is the design.** It follows no link it did not already know about and visits each URL once, so the pass is bounded by the *content* rather than by the site's shape. SH101 had already built the one thing needed — an origin-checked, operator-consented fetch — and the extraction into `ShAgentDeliveryProbe` is the point: two callers of a security-relevant guard is one caller too many for a private method, since the second copy is where the origin check eventually goes missing. The render digest now shares the client too, which also fixes a wart it never noticed — it built an `HttpClient` (and its selector thread, and a cold connection pool) per call.
  <br>**The exception is declared, never guessed.** A front end legitimately owns routes the CMS has never heard of, so the answer had to be *declared*, and the store whose whole purpose is "facts about this instance that are not content" already exists: a **SH114 memory note keyed `frontend-routes`**, globs (`*` inside a segment, `**` across), scoped to a site or instance-wide, attributed, carried in the context pack, surviving a prune, one `shio remember` away. And the rule that keeps it honest: **a declaration silences a guess but never a proof** — with fetching off the link is not reported, and with the delivery pass on it is still fetched, so a declared route the site 404s is an error, because the declaration made a claim and the claim is checkable. Suppression that survives contact with evidence is how a baseline rots into a blanket, which is the hazard SH142 was careful about. A pattern that is not a path is dropped rather than compiled — here the dangerous failure mode is the one that matches *everything*, and it would be silent.
  <br>**Not in the default set unless an operator asked for it.** `ShAgentCheck`'s law is that every group defaults to on, and this is an application of it rather than an exception: the group is in the defaults exactly when `shio.agent.render.allow-fetch` is set, because on every other instance it cannot run at all and including it would fail a report on the absence of a deployment. Naming it while fetching is off is a teaching **400** (`delivery-disabled`), for the reason SH143 refuses an unresolvable `folder=`: a check that silently covered nothing while answering `ok` is the worst false green there is. The same distinction settles "no site has a URL" — a **400** when the caller named the group, a per-site **warning** when it arrived by default, since a group that joined on its own must not fail a call that never asked.
  <br>**Three bounds, and every cut is visible.** `max-fetches` (50) bounds the count, `fetch-budget-millis` (15s) bounds the *time* — not the same bound, since fifty pages behind a slow front end is four minutes, which is not a verification call but a hang — and an unreachable origin ends that site's pass after **one** request, reporting **one** `delivery-unreachable`: fifty copies of "it is down" is a report nobody reads, and the site's other pages are *unknowable*, not broken. Everything skipped goes in `notes`, and `shio verify` now prints `notes` at all — they were invisible in that output until this needed them, which had been quietly costing SH143's truncated-feed note too.
  <br>**`routes` hands the unresolved links over instead of warning about them.** The two rules answer the same question, and a defect reported once as a maybe and once as a fact is a report the reader has to de-duplicate. Manifest: `deliveryProof`, reported separately from `renderFetch` even though one property governs both, because an agent reading only the latter would never learn that `link-unresolved` can be an error here. **Deliberately not on the MCP tool schema:** a tool description is re-sent every turn (P3), and on the instances where this is `false` it would be a tax for a capability that cannot run — the manifest is the discovery surface, and `shio_verify`'s `checks` argument passes the group through unchanged. - **SH154** — **The lint sees a section reference** ([ShPostReferenceFields](../shio-app/src/main/java/com/viglet/shio/api/agent/verify/ShPostReferenceFields.java), [ShAgentVerifyService](../shio-app/src/main/java/com/viglet/shio/api/agent/verify/ShAgentVerifyService.java)) and **SH169** — **the render digest composes the way the page does** ([ShAgentRenderService](../shio-app/src/main/java/com/viglet/shio/api/agent/verify/ShAgentRenderService.java)). Two shipped features, each correct alone, both blind to the pattern SH95 introduced: the `dangling-reference` rule knew a reference held as an **id** (`Content Select`, `File`) and not one held as a **friendly URL**, and the digest reads a post's own markup — which a section page has none of. So a page could name a section that did not exist and `verify` answered `ok`, and home, pricing and a genuinely blank page all hashed to `e3b0c442…`, the hash of nothing. The digest could answer neither question it exists for.
  <br>**One mechanism serves both, and picking it was most of the work.** A `Multi Select` is a free-form list of strings by design and most of them are tags, so neither reader could just treat values as URLs — that rule would report a defect for every tag on every post. The field now *declares* what it holds, in the model, which is the one place both readers already look: `widgetSettings: {"multiselect":{"references":"post"}}`. A **new key** rather than overloading the existing `multiselect.postType`, because that one says *which* type and a page's sections are deliberately heterogeneous — overloading it would mean naming one type and lying. A convention ("a field called `sections`") was the alternative and is unenforceable: nothing can check prose. The `@viglet/shio-model` DSL carries it (`references: "post"`), `@viglet/shio-sections` declares it on `Page`, and `pnpm -C shio-sections run emit` regenerated the two packages that ship it.
  <br>**The lint keeps both properties of the id-shaped rule:** an unpublished target on a published page stays the existing `unpublished-dependency` case — same failure, different spelling — and a target this credential cannot read is re-checked against the repository rather than reported as dangling, so the SH2 allow-list never manufactures a defect. A value that names a post of the wrong type (when `postType` narrows it) is its own `wrong-reference-type` finding.
  <br>**The digest reads the model, not a list of the eight first-party types.** A section's structure is not in one HTML field: the vocabulary's components render its title as a heading and its text fields as prose. So the mapping is stated once in terms of what the model says about a field — a title field becomes a heading, a markup field contributes its parsed structure, any other text field contributes its words — and it runs the *same parser*, so there is one notion of "structure" rather than a second path that would drift. A digest that knew the shipped section types by name would stop working the first time somebody wrote a ninth.
  <br>**An unresolvable section is marked, not skipped.** Contributing nothing is the original failure wearing a different hat: two different mistakes would hash the same. It contributes a heading naming the gap, so the digest moves when a reference breaks. The cost is real and stated: a page digest now reads N+1 posts, which is the same scoping pressure as **SH143**.

- **SH149** — **an empty folder is a file** ([content-files.mjs](../cli/src/content-files.mjs), [content-store.mjs](../cli/src/content-store.mjs), [content-sync.mjs](../cli/src/content-sync.mjs), [content-pull.mjs](../cli/src/commands/content-pull.mjs), [content-push.mjs](../cli/src/commands/content-push.mjs)). `shio/folders/<site>/<name-chain>/_folder.md`, frontmatter only, declared by `push --content` as a `folder.upsert`. Two roots cannot express the mistake.
  <br>**A marker declares only what nothing else does.** Writing one per folder would double a projection's file count to restate every post's own `folder:`, and each of those files would then be another thing to keep in sync. `implied` — the posts' folders plus every ancestor — is subtracted, and the skipped folders still count as *agreed* so the next pull cannot read them as deletions.
  <br>**Folders are in the base snapshot, and that is not incidental.** A marker on disk the server does not have is either a scaffold not yet pushed or a folder somebody deleted; existence alone cannot tell them apart, and each wrong guess loses real work (deleting the author's new declaration, or resurrecting a folder somebody removed). `reconcileFolders` takes the third value and decides. A snapshot written before this reads as "we have never agreed about any folder", which makes every server folder newly-added and every local marker locally-added — both safe, both self-correcting, so no version bump.
  <br>**A marker widens `--prune`'s scope, deliberately.** Declaring `/archive` means the tree owns `/archive`; the identical widening already happened the moment a *post* named it, so the marker reaches an existing rule by a different file rather than adding a rule. Documented instead of special-cased.
  <br>Two smaller refusals worth keeping: a marker whose path and `folder:` disagree is an error (SH134's lesson, which is also why it writes the two keys its path already implies), and **text in a marker is refused** rather than dropped — a folder holds posts, not prose, and silently discarding it loses something somebody wrote expecting it on the site. The folder list comes from the context pack's sitemap walked to completeness (no `GET /agent/folders` — law P10), and a walk that cannot finish marks the snapshot partial for SH146's reason: `--prune` deleting a folder takes every post beneath it.
- **SH150** — **a renamed file is a move, and the document grew one channel for intent** ([ShAgentDesiredState](../shio-app/src/main/java/com/viglet/shio/api/agent/dto/ShAgentDesiredState.java), [ShAgentDesiredStateService](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAgentDesiredStateService.java), [content-sync.mjs](../cli/src/content-sync.mjs), [content-files.mjs](../cli/src/content-files.mjs), [content-push.mjs](../cli/src/commands/content-push.mjs)). A rename is two file edits — the path and `url:`, which the format already refuses to let disagree — and to a pure state document that reads as one undeclared post at the old URL plus a new post at the new. `--prune` deleted the first and created the second, so what came out had a new id and none of the original's audit trail, version history or inbound references: the workaround SH134 exists to prevent, reached from the file side.
  <br>**Why a state document needs `moves` at all.** Everything else in the document is state, and that is exactly what makes an apply re-runnable. A move is *not* state — "this post is at /b" and "this post used to be at /a" describe the same world and imply different work — so no amount of declaring could express it. `moves` is therefore the one intent channel, kept as narrow as it can be: `{from, to?, folder?}`, compiled to `post.move` **after folders and before upserts** (the destination folder must exist; the upsert must then land on the moved post rather than create a second one beside it). It stays re-runnable because a move whose `from` is gone is a **noop** — without that, pushing the same tree twice would fail on "no post at /old".
  <br>**The prune interaction is the dangerous part, and it is where the real bug would have been.** The sweep reads the database *before any op has run*, so a renamed post is still sitting at its old URL and nothing in `posts` names it — it would be swept. At apply time the move runs first and the delete would find nothing, so content would survive; but the **plan** would list `deleting post:Blog/blog/old`, and SH108's confirm digest is taken over that list. A rename would have asked the operator to confirm destroying the post it was preserving. A move's `from` now counts as declared, and its `folder` as a placement.
  <br>**Detection is three signals, in order of what they prove.** `movedFrom: <old url>` in frontmatter is an instruction like `publish:` — never written by a pull, preserved through a merge, and the only signal that survives a rename *plus* a rewrite, since after a rewrite there is nothing left to match on. Identical content (type, folder, every field) at a vanished address and a new one covers the common case — `git mv`, edit `url:`, push — with nothing asked of the author. And a `folder:` that differs from the server's is the third, which is **a defect this fixed rather than a rename**: `post.upsert` deliberately does not relocate an existing post, so editing a file's `folder:` was a push that reported success and moved nothing.
  <br>**Ambiguity is refused; probability is reported.** Two files that could each be the same rename are a one-in-two chance of moving the wrong post's history, so the push stops and names the candidates — as does a `movedFrom` pointing at a post the tree still declares. A pair that is plausible but unprovable (same type, different content) is *printed*, with the `movedFrom:` line to add, because the alternative is a delete-plus-create that destroys history in silence. A `movedFrom` equal to the file's own URL is refused at parse time: it is the likely slip (the *new* value pasted in), and left alone it compiles to a move onto itself whose server error says nothing about the actual mistake.
  <br>**Two client invariants that are easy to get wrong**, both of which turn the fix into the bug it fixes: a moved post's old address must leave `removed`, or `--prune` deletes the post the move just preserved; and it must not be re-added to the base snapshot from the server read — which was taken *before* the move — or the next run offers to prune it. Fixing the second also caught push's `writeBase` dropping SH149's folder agreement.
  <br>**Not everywhere, deliberately.** A blueprint may not declare `moves` (`CONTENT_KEYS` already refuses it): a package is an appliable *starting point*, so everything it declares is content it brings, and renaming the caller's live pages is not its business. `shio_apply` does not take it either — it is the largest tool on the surface at 437 of a 460 ceiling, and `shio_write` already carries `post.move` as one value in an op enum that exists. Same reasoning as SH151/SH152, and here the budget and the design agree.

## Block J — Blueprints (appliable units) + Claude Code plugin (SH74)

> The block removes the *third* cost in a typical build: re-deriving a starting point that
> somebody has already derived. Design law P8 says skipping steps needs **appliable** units,
> so a blueprint is not a recipe an agent reads and reimplements — it is a package the
> instance applies, with a plan first and a proof afterwards. The section vocabulary is the
> other half of the same idea: a page made of *known* sections is a page a later session can
> change without an archaeology pass.

- **SH92** — **Blueprint package format** ([com.viglet.shio.blueprint](../shio-app/src/main/java/com/viglet/shio/blueprint)). A package is a directory with a [ShBlueprintManifest](../shio-app/src/main/java/com/viglet/shio/blueprint/dto/ShBlueprintManifest.java) (`blueprint.json`), post-type files, content documents, optional front-end files and a `verify` promise. **Nothing in it is a new serialization:** `postTypes` are SH16 `ShPostTypeDef`s (the JSON `shio pull` writes, so a package's model can be authored with `@viglet/shio-model` and diffed with `shio push --check`) and `content` files are SH82 desired-state documents, which is what keeps the format from becoming a third contract (P10). The design calls worth naming: (1) **a package may not name its own site** — the site is the caller's, so the common case (apply *into* an existing instance) works and a `site` key in a content document is refused at load rather than ignored, because an ignored key looks like it worked; (2) **a package may not `prune`** — prune's blast radius depends on what the document's author forgot to mention (P7) and that author is a package the user did not write; (3) **parameters are a JSON Schema, and substitution is `{{name}}` and nothing else** — no conditionals, no expressions, because every one of those turns a package from data into a program whose output cannot be predicted by reading it (P5); (4) **`site` is a reserved parameter**, always available, never declarable. [ShBlueprintParams](../shio-app/src/main/java/com/viglet/shio/blueprint/ShBlueprintParams.java) makes every parameter mistake a teaching 400 with `allowed`/`didYouMean` — an unknown parameter is *refused*, not ignored, since a silently-dropped `brandName` yields a site full of defaults with nothing to suspect. **The load-time validation is the part that matters** ([ShBlueprintRegistry](../shio-app/src/main/java/com/viglet/shio/blueprint/ShBlueprintRegistry.java)): a referenced file that is not in the package, a path that escapes it, an unknown manifest key, a `{{placeholder}}` with no declared parameter, and a `verify.posts` entry the package's own content never declares are all the *author's* mistakes, and all of them would otherwise surface as a stranger's half-applied site. A malformed package is a **409, not a 400** — nothing the caller sent caused it, and a 400 would send an agent into a retry loop over its own arguments. [ShBlueprintCodec](../shio-app/src/main/java/com/viglet/shio/blueprint/ShBlueprintCodec.java) carries the same `FAIL_ON_NULL_FOR_PRIMITIVES=false` decision `ShExchangePackageCodec` made for SH68 and for the same reason: the canonical authoring form omits delivered-only fields (`managed`), and Jackson 3 rejects an absent primitive by default. 8 tests ([ShBlueprintRegistryTest](../shio-app/src/test/java/com/viglet/shio/blueprint/ShBlueprintRegistryTest.java), no Spring context — it runs in milliseconds so it can run on every change to a package) + 8 ([ShBlueprintParamsTest](../shio-app/src/test/java/com/viglet/shio/blueprint/ShBlueprintParamsTest.java)). → was §XI.1
- **SH93** — **Applying one** (`GET /api/v2/agent/blueprints`, `GET /agent/blueprints/{name}`, `POST /agent/blueprints/{name}/apply`, `shio blueprints`, `shio apply --blueprint`, and `blueprint`/`params` on `shio_apply`). [ShBlueprintService](../shio-app/src/main/java/com/viglet/shio/blueprint/ShBlueprintService.java) resolves the parameters, substitutes them, compiles the result into a post-type list plus **one** merged desired-state document (one document, so a package cannot half-apply and the compiler's folders-then-posts-then-publishes ordering holds), and hands both to [ShBlueprintWriteService](../shio-app/src/main/java/com/viglet/shio/blueprint/ShBlueprintWriteService.java). Four decisions: (1) **the model is provisioned, never upserted** — `provisionFromDef` leaves an existing post-type exactly as it is, including a field a human added, because a blueprint seeds a model and does not own one; upserting would also flip SH66's `managed` flag and lock the type in the console from a package the user never wrote; (2) **the plan provisions inside its transaction and rolls back** — the content planner resolves every post's type against the live model, so without this a plan for a package bringing its own types would fail on its first post with "no post-type named Article" and be useless for exactly the case blueprints exist for. This is the technique `ShAgentBatchService` *refuses* for content, and the difference is real rather than convenient: content writes emit audit rows, webhooks, lifecycle events and quota movements that a rollback cannot take back, while provisioning a post-type emits none of those. The content half of the plan is still a true dry run and writes nothing at all — the test asserts the post-type is **absent** afterwards, which is the only way to see it; (3) **a name collision is reported, not resolved** — a site created through the console already carries the SH71 bootstrap `Page` (`title` + `content`) while the section vocabulary's `Page` has `sections`, so the older type wins and the response names the fields it lacks, because the alternative is content written into a field the console cannot render (**SH152** reconciles); (4) **the front-end files are returned, never written** — they belong in the caller's project and the server cannot see a working tree, so `shio apply --blueprint` writes them (never over an existing file without `--force`) and an MCP-only caller is told what it has *not* got (P9). 6 end-to-end tests ([ShBlueprintApplyTest](../shio-app/src/test/java/com/viglet/shio/blueprint/ShBlueprintApplyTest.java)) + 11 CLI ([blueprints.test.mjs](../cli/test/blueprints.test.mjs)). → was §XI.2
- **SH94** — **First-party set**: `blog` (an Article type, `/blog`, three published samples), `docs` (a DocPage type and a `/docs` tree with guides and reference), `product-catalog` (a Product type with SKU, price and a Relator spec list, plus an accessories subsection), `marketing-site` (home, pricing and about, each composed of sections) and `landing` (one campaign page of four sections) — [shio-app/src/main/resources/blueprints](../shio-app/src/main/resources/blueprints). Every package declares a `verify` promise, and the promise is checked **twice**: at load against the package's own content (so a promise nobody could keep never ships) and after an apply against the instance, alongside the SH99 lint over the target site. That second check is reported rather than rolled back — the content apply is already atomic and re-applying converges, so the useful answer to "it promised /pricing and it is not there" is a report the caller can act on plus the findings that usually explain why. A required parameter is used where a package genuinely cannot invent a value (`brand`, `productName`) and a default where it can (`blogTitle`, `currency`); `shio apply --blueprint` exits **non-zero** when the verification fails, so an unattended apply cannot report success it did not earn. → was §XI.3
- **SH95** — **Section library** ([`@viglet/shio-sections`](../shio-sections)) — the highest-leverage item in the block, and the one that makes *changing* a site cheap rather than archaeological. Eight post-types (`Page` plus `SectionHero`, `SectionFeatureGrid`, `SectionCta`, `SectionLogoWall`, `SectionTestimonial`, `SectionFaq`, `SectionRichText`) authored with `@viglet/shio-model` in [post-types.ts](../shio-sections/src/post-types.ts), and the matching React components in [components.tsx](../shio-sections/src/components.tsx) with a `SECTION_COMPONENTS` registry and a `<Sections>` dispatcher. **The composition rule:** a `Page` names its sections by **friendly URL, in order**, in a Multi Select — not by id (SH79 exists so no UUID has to survive between calls), and not as a Relator (whose children are one fixed shape, while a page's sections are deliberately heterogeneous). **The components are unstyled and semantic on purpose:** they ship the *structure* — heading level, landmark, alt text — and leave design to the site's CSS via stable `shio-*` class names, because a package that shipped opinions about type scale would be replaced on day one, and because SH101's digest reads structure, so a shared vocabulary is only verifiable if structure is the shared part. `<Sections>` takes **resolved** sections rather than fetching them, so the vocabulary works from a server component, a loader or a static build. The definitions ship into the two blueprints that use them as canonical JSON (a running instance reads packages off the classpath and cannot run a JS build), generated by [scripts/emit.mjs](../shio-sections/scripts/emit.mjs) and guarded by [emit.test.mjs](../shio-sections/test/emit.test.mjs) — two copies of anything eventually disagree, so the second is generated and the build fails the moment they diverge. 12 tests, including a source-level guard that every section post-type has a component and that every `<img>` the vocabulary renders carries `alt`. → was §XI.4
- **SH97** — **Claude Code plugin** ([claude-plugin/](../claude-plugin), published through the repo-root [marketplace](../.claude-plugin/marketplace.json)): `claude plugin marketplace add openviglet/shio && claude plugin install shio`. An MCP server entry that runs the CLI's stdio bridge through `npx` (nothing to install first), three skills — `shio-site` (addressing, `shio_apply`, draft-then-publish, moves), `shio-content-model` (post-types as code, the widget list, the traps) and `shio-verify` (how to read the lint's severities, digests, the bounded incident window) — three commands (`/shio-start`, `/shio-blueprint`, `/shio-check`), and an `AGENTS.fragment.md` for projects whose sessions will not have the plugin. This is the **distribution channel for the whole concept**: it is how a developer adopts agent-native Shio in one command, and what the skills encode are the rules that are expensive to learn by making the mistake (path addressing, plan before write, DRAFT by default, `post.move` for a rename, verify before reporting done). The fragment says out loud that it is hand-written and will rot, and points at SH115. 6 tests ([plugin.test.mjs](../claude-plugin/test/plugin.test.mjs)) validate the manifests, that the marketplace's `source` exists, that every skill's description states its trigger (the description is the *only* thing that decides whether a skill loads), that no command that writes omits `dryRun` or the DRAFT rule, and that no credential is defaulted in `.mcp.json`. → was §XI.6
- **Block J wiring** — manifest: `blueprints` flips to `true` (reported `false` through Blocks H, K and I so that flipping it would mean a real registry rather than an intention), two endpoints join the curated index, and the blueprint hint folds into the existing write step so `startHere` stays five lines. MCP: `shio_apply` gains `blueprint` + `params` rather than an eleventh tool — "converge to this document" and "converge to this package" are one decision with two inputs, and a `shio_blueprint` of its own would have cost more schema than the two arguments did while making "which tool" a question the model has to answer; the new `shio://blueprints` resource is the catalogue, terse and without per-package schemas so choosing between five packages does not cost five schemas. The SH132 budgets rise for it (`max-per-tool` 400 → 460, `total` 2110 → 2160, both justified in [token-budgets.properties](../shio-app/src/test/resources/token-budgets.properties)) and the SH130 golden was regenerated — the diff is exactly the two new parameters and the new resource. The `new-site` and `add-section` MCP prompts now check the catalogue *before* modelling by hand, because a procedure that omits that step teaches the agent to pay Block J's cost anyway. CLI: `shio blueprints [name]` and `shio apply --blueprint` with `--param`/`--params`/`--site`/`--force`; `parseArgs` gained a `repeatable` option so a repeated `--param` is collected rather than reduced to the last one, which would apply a package with defaults the caller believed they had overridden. Parameter values are coerced against the package's **declared** types (a terminal has only strings) rather than by guessing from their shape, which would send a version number or a SKU as a number.

## Block M — Token economy, measured (SH74)

> The brief asks that this get cheaper over time, so the block's job was to stop asserting
> it. Every number below is produced by the build: what a canonical job costs, what each
> canonical response costs, and how much of both an agent avoids paying twice. The one
> place the measurement disagrees with the concept spec is recorded as a task rather than
> rounded off.

- **SH112** — **Task benchmark harness** ([ShAgentTaskBenchmarkTest](../shio-app/src/test/java/com/viglet/shio/api/agent/benchmark/ShAgentTaskBenchmarkTest.java), [ShAgentBenchmark](../shio-app/src/test/java/com/viglet/shio/api/agent/benchmark/ShAgentBenchmark.java)). Four canonical jobs — build a marketing site, add a post-type and ten posts, fix a broken link, translate a site — each run **twice**: once over the agent surface and once over the same instance's id-keyed console/CDA endpoints, the way a client without addressing, batching or a context pack would have to. **The baseline is the point.** A single-path benchmark only says whether today is worse than yesterday; the ratio is what makes the claim falsifiable. Calls, tokens (request *and* response — a batch of ten posts spends most of its cost upward, and counting only responses would make a chatty writer look cheap) and wall clock are recorded; calls, tokens and both ratios are asserted against ceilings in [token-budgets.properties](../shio-app/src/test/resources/token-budgets.properties); **wall clock is recorded and never asserted**, because CI timing is noise at this scale and a benchmark that fails on noise gets deleted. The run is written to `target/agent-benchmark.json` so a release can archive it.
  <br>**What it measured (2026.3):** tokens **3.8×–23.3×** cheaper on the agent path, so the ≈10× target is met on three tasks of four — the fourth is the blueprint apply, which also provisions eight post-types the hand-built baseline assumes into existence, and the comparison is left understating the agent path rather than adjusted to flatter it. Tool calls: **1.8×–3.3×** against a ≈6× target, **not met anywhere**. The floors in the properties file are set at what the surface actually achieves, not at what the spec asked for, because a ceiling nothing can pass is a ceiling somebody disables; the gap itself is **SH157**.
  <br>**What driving the write surface over real HTTP found:** Jackson 3 enables `FAIL_ON_NULL_FOR_PRIMITIVES` by default, and for a *record* an absent property reaches the canonical constructor as a null — so the most natural call the protocol has, `POST /api/v2/agent/batch {"ops":[…]}` without `dryRun`, answered **400 "Request body could not be read"** without naming a field. Same for a blueprint apply without `dryRun` and a post-type definition without `system`. It broke P2 and P6 at once and was invisible to every test that builds the request record in Java, which is how it survived Blocks H, I, J and K. Fixed in [application.properties](../shio-app/src/main/resources/application.properties) and mirrored into the test properties — which *shadow* the main file rather than merging with it, the drift that let it hide (**SH158** guards the class).
- **SH113** — **Response budget enforcement** ([ShAgentResponseBudgetTest](../shio-app/src/test/java/com/viglet/shio/api/agent/benchmark/ShAgentResponseBudgetTest.java)). Eleven canonical responses measured through the instance's own `X-Shio-Est-Tokens` (SH124) — not re-tokenized locally, or the number an operator logs and the number CI guards would be two different numbers with only one of them checked — against ceilings in the same `token-budgets.properties` SH132 already uses. It is the cheap always-on guard between benchmark runs, and what it defends against is not a bad commit but entropy: a convenient field added to a listing DTO, twelve tokens per row, three releases, entity-shaped JSON again. **Three payloads resist a fixed ceiling and are handled rather than ignored:** the context pack's `model` section describes the whole instance, so it is guarded **one type row at a time** (`context.type-row`), which is both order-independent and the better guard — a field added to the type shape multiplies by the size of somebody's content model; `conventions` is prose that grows with the instance and is bounded in production by `shio.agent.memory.*` instead; `diagnostics` is an in-memory window whose size is an operational fact, not a shape. Two of the three tests are claims rather than ceilings: **terse must cost less than JSON** (SH78's entire justification — if it ever inverts, the second encoding should be deleted rather than kept out of politeness) and **`ids=true` must cost meaningfully more** (so SH121's measurement stays a measurement rather than becoming folklore).
- **SH114** — **Instance memory / conventions store** (`GET/PUT/DELETE /api/v2/agent/memory`, `shio remember`, [ShAgentMemoryService](../shio-app/src/main/java/com/viglet/shio/api/agent/memory/ShAgentMemoryService.java), [ShAgentMemoryEntry](../shio-app/src/main/java/com/viglet/shio/persistence/model/agent/ShAgentMemoryEntry.java), `v2026.3.9.yaml`). The only piece in the block that **compounds**: everything else makes one session cheaper, a note makes every session after it cheaper. Keyed notes ("this site's blog uses `Article`, not `Post`") are served in the context pack's `conventions`, so the read path costs nothing — an agent that read the context has already read the memory. Five decisions worth keeping: (1) **a table, not content** — memory is read on the hot path, never delivered, and must survive a `prune`; modelled as content it would sit inside the very desired-state documents it exists to inform, and an agent that forgot to declare its own memory would delete it; (2) **upsert by `(tenant, scope, key)` with a unique index** — re-stating a convention rewrites one row instead of leaving the next session two near-duplicates to reconcile; (3) **`scope` is `''` for instance-wide, never `NULL`**, because SQL indexes do not treat `NULL`s as equal and a nullable scope would silently admit duplicates; (4) **attribution is a field, not a workflow** — every note names its author and the pack prints it, so a human's instruction and another agent's inference can be weighed differently, which is far cheaper than an approval queue for something that misleads the next session rather than changing the site (SH109 gates agent writes across the board); (5) **derived conventions are printed before remembered ones**, because a derived line is true by construction and a remembered one is somebody's claim. **No MCP tool**, deliberately: a tool schema is paid on every turn of every session (P3) and a coding agent has a shell, so `shio remember` costs nothing per turn and the context pack says it exists — which is also what makes the store self-sustaining. **SH160** is the open question for a client with no terminal. 12 tests.
- **SH115** — **`AGENTS.md` generator** (`?format=agents-md`, `shio context --as agents-md`, [ShAgentAgentsMd](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAgentAgentsMd.java)). The same pack rendered as project agent instructions, for the moment *before* an agent has decided to work on content — a harness loads a file, it does not make a call. So the rendering is instruction-shaped rather than data-shaped: it opens with what to do, the model table exists to stop the agent inventing a post-type rather than to be a schema reference, and **individual pages are deliberately left out** (a generated file that lists content goes stale on the next publish and grows without bound; `find` answers "which pages" in one always-current call). It says out loud that it is generated and that the endpoint is the authority, and it carries the pack's digest so a reviewer can tell at a glance whether a checked-in file still matches the instance. Nothing measured is rendered — no token counts, no timestamps — because a generated file that changes on every run is a generated file nobody commits. One behaviour change came with it: an **unknown `format` is now a teaching 400** rather than a silent fallback to JSON, because with two renderings a typo cost a slightly wrong payload and with three, `agent-md` would quietly return JSON and the caller would conclude the feature does not exist.
- **SH116** — **Agent-read caching** ([ShAgentEtag](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAgentEtag.java)). Strong ETags on the manifest, the context pack and the blueprint catalogue; `If-None-Match` on an unchanged instance answers **304**, which measures as **zero** on `X-Shio-Est-Tokens` — the assertion is on that number, because "re-reading the context is free" is either visible there or it is marketing. What this changes is a *decision*: re-checking the context was a trade (a few thousand tokens for certainty, or work from a remembered digest and risk being wrong) and is now the cheap default. **The tag is over a representation, not a state.** The SH77 digest deliberately covers content only, so JSON and terse share one — correct for "has anything changed?", wrong for `If-None-Match`, where a terse-cached client handed a JSON tag would keep the wrong bytes; every tag mixes the digest with `format` and `ids`. `Cache-Control: no-cache` (store it, but ask first) rather than a freshness lifetime, because content can change at any moment and revalidation costs a round trip and no tokens. Note what is *not* saved: the server still builds the pack to know its digest, and that is the right trade — the scarce resource is the caller's context window, and a cached digest that could go stale would break the only guarantee that makes the scheme usable.
- **SH127** — **Lean the delivery JSON and the SDK types, together** (`@JsonInclude(NON_NULL)` on the CDA read DTOs; `string | null` → `field?: string` in [shio-client/src/types.ts](../shio-client/src/types.ts); [ShCdaJsonLeanTest](../shio-app/src/test/java/com/viglet/shio/api/cda/ShCdaJsonLeanTest.java)). SH125 leaned the agent surface and stopped here on purpose: omitting a null while the published types still promised one would have handed every typed consumer an `undefined` from a comparison it believed was exhaustive — the payload gets smaller and the contract gets a lie in it. Both halves therefore moved in one commit. **The rule survives unchanged: NON_NULL, never NON_DEFAULT.** A null says nothing that absence does not already say; a `false` or a `0` frequently *is* the answer — `published:false` is the difference between a draft and a page nobody mentioned, and `totalPosts:0` answers "is this folder empty?". The visible payoff on the agent side is that the context pack's `model` section no longer inherits a null through the shared `ShCdaSchemaField` (P10 composition over a contract that could not be leaned unilaterally), and [ShAgentJsonLeanTest](../shio-app/src/test/java/com/viglet/shio/api/agent/ShAgentJsonLeanTest.java)'s characterization of that cost is **inverted rather than deleted**, so a null re-introduced on the delivery shape still surfaces at both ends.
- **Block M wiring** — manifest: `instanceMemory`, `conditionalReads` and `agentsMd` flip to `true`, and `PUT /agent/memory` joins the curated endpoint index. The index is capped at 30 by [ShAgentManifestTest](../shio-app/src/test/java/com/viglet/shio/api/agent/ShAgentManifestTest.java), so it **displaced** an entry rather than raising the ceiling: `/cda/post/by-url`, whose own description ("the cheapest addressing available today") was a hedge written before addressing existed and which SH79 plus `/agent/resolve` and `/agent/read` now do better without a site id. The endpoint itself is unchanged and still served. Context pack: memory rides in `conventions` behind a `[memory:key@site by author]` marker, and one derived line tells the agent the store exists and how to write to it — a store nobody writes to never pays back the row it costs. CLI: `shio remember [<key> "<note>"]` with `--forget`, `--site` and `--limit`, plus `--as agents-md` on `shio context`; a truncated listing says so rather than reading as the whole set (SH138's rule).

## Block N — Realignment of what already shipped (SH74)

> The reorientation was mostly additive, but it did invalidate some existing choices, and
> this block spent them. Two of the four tasks removed a *second* way of saying something
> the platform already said; one folded a second half-format into the real one; one closed a
> drift nothing was watching. The block's most useful output is not a feature — it is that
> **fixing the baseline cost the agent surface most of its measured token advantage**, which
> is recorded below rather than rounded off.

- **SH117** — **One name-keyed post-type surface** ([ShPostTypeAPI](../shio-app/src/main/java/com/viglet/shio/api/post/type/ShPostTypeAPI.java), [ShPostTypeAdminService](../shio-app/src/main/java/com/viglet/shio/api/post/type/ShPostTypeAdminService.java), [ShPostTypeApiTest](../shio-app/src/test/java/com/viglet/shio/api/post/type/ShPostTypeApiTest.java)). The id-keyed, entity-shaped `/api/v2/post/type` is **retired** and the React console reads and writes the same name-keyed, lossless `/api/v2/post-type` the CLI and the agent use. Two APIs for one concept was a tax paid on every agent session ("which one, and by id or by name?") and a straight violation of P5/P10.
  <br>**The load-bearing decision is what `managed` means on a write.** It became a `Boolean`, because absent and `false` have to differ: *absent* (the CLI's canonical serialization omits the key) is a code-owned write — mark it managed, and let the owner keep converging; *`false`* is a hand edit — mark it unmanaged, and refuse against a managed type with a 409 rather than silently winning a race with the repository. Get that backwards in either direction and unifying the APIs either locks the console out of every type it creates or lets it quietly overwrite the model a repo owns. It is a UX guard, not an ACL: any caller may claim either, and what it must never do is let one writer's convention overwrite the other's without saying so.
  <br>**Two verbs, not one.** `PUT /{name}` stays the idempotent upsert — converging a model that is already declared has to be a no-op or `shio push --check` means nothing — and `POST` creates and conflicts, because a name collision in the console's "new post-type" form is a mistake to report, not a content model to replace.
  <br>**`POST /api/v2/post-unified` now accepts `postType` by name** beside `postTypeId`. The console picks a post-type off a name-keyed surface and has no id to send; resolving the name server-side is one lookup where the id lives, instead of a round trip whose only purpose is translating a name the caller already knows. Unknown or absent is a teaching 400 carrying the installed catalogue.
  <br>**The security half is not incidental.** `/api/v2/post-type` was blanket CSRF-exempt so the stateless CLI could reach it; with a logged-in browser on the same path that exemption would have made "unify the two APIs" quietly mean "drop CSRF protection on the content model". [ShStatelessRequestMatcher](../shio-app/src/main/java/com/viglet/shio/spring/security/ShStatelessRequestMatcher.java) narrows it to callers holding no session cookie — the right discriminator because the cookie is exactly the credential a cross-site request replays, and because it is readable *before* authentication, which a principal-based check would not be (`CsrfFilter` runs ahead of the authentication filters).
  <br>**Rename is not on this surface, deliberately.** The console's API-name field is read-only: a `PUT` to a new name would create a second post-type and leave the first one's content behind, which is SH134's lesson for posts. **SH163** is the task.
- **SH119** — **The Next.js starter is a blueprint** (`blueprints/nextjs-starter/`, [create-shio-app/src/emit.mjs](../create-shio-app/src/emit.mjs), `shio init --blueprint`). `create-shio-app`'s `template/` and the blueprint format were two half-formats for one idea — a tree of files with `{{placeholder}}` substitution — and neither was the other. The template is now also a first-party package: a `Page` model, two published pages, and the whole App Router project as carried `files`, with a `verify` promise like every other package.
  <br>**`template/` stays the single source of truth**, and the package is generated from it by `pnpm -C create-shio-app run emit` with `test/emit.test.mjs` failing the build on drift. A running instance reads packages off the classpath and cannot run a JS build, so the second copy is unavoidable — and an unavoidable second copy needs a guard, or `npm create shio-app` and `shio init --blueprint nextjs-starter` slowly stop producing the same project with nothing to say so. Same discipline as `shio-sections`' emit.
  <br>**Substitution is split by who knows the answer, and the rule is shared.** The server substitutes a package's *content*; the client substitutes its *carried files*, because the one parameter a starter needs is the project's own local identity and because the server never writes a project file anyway. The JS regex is now character-for-character `ShBlueprintParams`', so a package cannot have a parameter one half fills in and the other leaves standing — narrow enough that JSX (`style={{ color: "#666" }}`) is not a placeholder, which is what lets a starter tree carry both. `shio apply --blueprint` also substitutes now; it had been writing carried files verbatim, so a `{{param}}` landed on disk unsubstituted while the same run filled it in throughout the content.
  <br>**One production bug fell out of carrying a Next.js tree:** the registry's path-escape guard was `path.contains("..")`, which also rejects `app/[...slug]/page.tsx`. A dot run inside a segment is a filename; only a segment that *is* `..` traverses. Asserted directly in both directions — a security check that has been loosened is exactly the kind that must be shown still catching what it was written for (§XIV.4's lesson, applied to itself).
- **SH120** — **Console navigation reads adopt the CDA shapes** ([ShConsoleListing](../shio-app/src/main/java/com/viglet/shio/api/object/dto/ShConsoleListing.java), [ShConsoleNavigationMapper](../shio-app/src/main/java/com/viglet/shio/api/object/ShConsoleNavigationMapper.java), [ShConsoleShapeOverlapTest](../shio-app/src/test/java/com/viglet/shio/api/object/ShConsoleShapeOverlapTest.java)). `/object/{id}/path` and `/folder/{id}/path` return the CDA's own `ShCdaPath` — the shapes were already identical apart from `shSite` versus `site`. `/object/{id}/list` returns `ShCdaListing`'s `{folderId, folders, posts}` envelope with rows that are **strict supersets** of `ShCdaFolder` / `ShCdaPostSummary`: the CDA's components first, name for name and type for type, then the fields a console has and a delivery API cannot express (draft `state`/`published`/`publishStatus`, manual `position`, the post-type's human `title`).
  <br>**What it replaced was worse than a naming problem.** The listing serialized the `ShFolder`/`ShPostUnified` entities, so browsing a folder of five posts read each post's attributes, its folder, its folder's site and its post-type's whole field tree in order to render five rows. It also stopped repeating the site and the breadcrumb: `/path` is the one endpoint that answers "where am I", and the listing's copy was the one that would go stale, because it is the response people add fields to.
  <br>**A superset, not the record itself** — the CDA delivers published content and has no way to say "draft", and a console's job includes saying it. The guard is a shape test rather than a convention: a shared component that drifts in name, order or type fails the build (the SH162 mirror-test pattern, applied inside the backend). Paging is deliberately *not* copied: this listing returns a folder's children whole, so `page`/`size`/`totalPosts` would be three constants pretending to be a contract. That it is unpaged is a real limitation, filed as **SH165**.
  <br>One latent console bug surfaced on the way: the post-type picker read `/path` as a flat array, a shape the endpoint never returned, so its breadcrumb had always been just "Sites". One spelling everywhere is what stops that being an easy mistake to make.
- **SH162** — **The SDK type mirror is complete, and stays complete** ([ShCdaTypeScriptMirrorTest](../shio-app/src/test/java/com/viglet/shio/api/cda/ShCdaTypeScriptMirrorTest.java)). `ShCdaPost` had delivered `locale` + `availableLocales` since SH52 — the two fields a headless front end needs for a language switcher — and `@viglet/shio-client`'s `types.ts` declared neither, so the one feature the types exist to make usable was invisible to a typed consumer without a cast. The fields are added; the task is the **test**, because the drift was invisible precisely because nothing compared the two shapes and will happen again the next time a DTO grows. Names must match one-for-one **in both directions** (a component with no property is a feature the SDK cannot see; a property with no component is a field the CDA dropped and the SDK still promises), a new DTO must be listed as mirrored or as deliberately unmirrored *with a reason*, and primitives may not be declared optional because SH127 omits nulls and nothing else. Types are deliberately not compared — `Instant` is delivered as an ISO string and `JsonNode` as an arbitrary object, so a mapping table would be a second contract to keep in sync for far less than it costs. The parser self-tests against known content and against a synthetic drift, per §XIV.4: a lint that matches nothing passes forever.
- **What the block did to the measurement, stated plainly.** Block M measured **3.8×–23.3×** cheaper on tokens. Block N measures **2.6×–12.6×** against an *unchanged* agent path, and the entire difference is SH117 and SH120 fixing the baseline: post-type listings stopped shipping ids, widget objects, dates and owners, and folder listings stopped shipping entity graphs (`fix-broken-link`'s baseline 7145 → 3877, `translate-site`'s 10033 → 5539, both roughly halved). **Tokens now clear the spec's ≈10× on one task of four, down from three; tool calls clear ≈6× nowhere, best 3.2×.** So a large part of the advantage was never the protocol — it was the console reads being entity-shaped, and it is now on both sides. What remains is the part worth defending: addressing instead of id round trips, one batch instead of N writes, a context pack instead of a crawl, a lint that names the defective post instead of a read-everything sweep. The floors in [token-budgets.properties](../shio-app/src/test/resources/token-budgets.properties) drop with the measurement rather than being defended, and the file says all of this at length. **SH164** owns re-establishing the token claim on its actual sources.

## Block L — Agent safety & human-in-the-loop (SH74)

> The block that makes the rest adoptable. An agent-driven CMS is only usable if the answer to
> "what if it gets it wrong" is a mechanism rather than a promise, and the three guards here are
> deliberately different shapes because they fail differently: a credential that cannot publish,
> a delete that needs the plan it was shown, and a queue that can put things back.
>
> **The invariant held throughout:** the agent path is never a privilege escalation. Every guard
> is *narrower* than what an agent could reach before — nothing on this surface gained a
> capability, and the SH22 tenant isolation, the SH54 ACL and the SH2 site allow-list still
> decide everything they decided before.

- **SH106** — **`AGENT` token scope + session identity** ([ShApiTokenScope](../shio-app/src/main/java/com/viglet/shio/persistence/model/token/ShApiTokenScope.java), [ShApiTokenFilter](../shio-app/src/main/java/com/viglet/shio/spring/security/auth/ShApiTokenFilter.java), [ShAgentSessionContext](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAgentSessionContext.java), [ShAgentSessionFilter](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAgentSessionFilter.java), [v2026.3.11.yaml](../shio-app/src/main/resources/db/changelog/v2026.3.11.yaml)). Until now an agent ran on one of two credentials and both were wrong: a `WRITE` CDA token — the Universal Editor's key, which patches published content outside the agent protocol's guards — or a console username and password, which is every capability the human has and cannot expire. `AGENT` is the third: it writes on `/api/v2/agent/**` and `/mcp`, reads drafts like `PREVIEW`, carries `ROLE_AGENT`, and deliberately **not** `ROLE_CDA_WRITE`. On the CDA it stays read-only, which is the entire reason it is a scope of its own rather than an alias for `WRITE`. It extends the SH2/SH5/SH13 model (expiry, per-site allow-list, rate limit) instead of adding a parallel one (P10).
  <br>**The session id got the column SH75 deferred.** `ShHistory.agent_session_id` makes "show me everything that run changed" a `where` clause instead of a `LIKE` over an actor string, and `owner` went back to naming only the human whose credential was used — one fact per field. Rows written before this keep the old `alice (agent:7f3c…)` suffix; they predate the column and nothing can honestly backfill them.
  <br>**It is no longer MCP's session.** The REST agent surface writes too — `/agent/batch`, `/agent/apply`, everything the CLI drives — and a review queue that could only see MCP's changes would have a hole in it exactly where the most common client is. `ShAgentSessionFilter` accepts the same `Mcp-Session-Id` header on the agent namespace; it deliberately **does not mint one per request**, because a session is a *run*, and one session per call is the same as having none — the reviewer would face two hundred one-change sessions instead of one thing to approve.
- **SH107** — **Draft-by-default + publish gate** (`api_token.may_publish`, [ShAgentBatchService](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAgentBatchService.java)). Agent writes already landed in DRAFT and publishing was already a separate op; what was missing is that anything able to write was able to publish. `mayPublish` is now a per-credential capability, **off unless granted**, enforced on the batch path — which is also the apply path and the blueprint path, because a desired-state document compiles to `post.publish` ops before it reaches the writer. One check, not four.
  <br>**Two deliberate calls.** It is checked **before the first write**, so a refusal is "you cannot publish" rather than a half-built site with a 403 at the end; and it refuses a **`dryRun` too**, because an agent should learn it cannot publish while planning, not after building twelve pages around the assumption. A console-authenticated caller has no token and is unaffected — the SH54 ACL is what bounds a human — and the SH10 CDA write path is untouched, because there a person is the one clicking.
  <br>**It is a tightening, and the changelog says so:** an existing `WRITE` token that used to publish through the agent surface now needs `mayPublish`. That is the point of the task; the alternative default would have made the flag decorative.
- **SH108** — **Destructive-op confirm tokens** ([ShAgentConfirm](../shio-app/src/main/java/com/viglet/shio/api/agent/ShAgentConfirm.java)). `post.delete`, `folder.delete` and any `prune` that would remove something take two calls: a `dryRun` hands back a `confirm` digest over the deletions, and the real run must send it back. The token makes two promises at once — an agent cannot destroy what it did not just render, and it cannot destroy something that **changed underneath it**, because a prune re-derives its deletions from current state and a page somebody else added since the plan moves the digest.
  <br>**What it covers is exactly the deletions**, sorted so the same intent always hashes the same (P5), and nothing else: re-confirming a document because a headline changed would train callers to paste the token back without reading, and a confirmation nobody reads is worse than none. A batch that destroys nothing needs no token and is handed none. Absent is a **428** with the token and the list; wrong is a **409** naming what would go now. Both are bounded at 20 addresses with a real count and a pointer to the plan — SH138's rule, applied to the one list where truncation is most dangerous.
  <br>**The CLI does the two-step for you** (`applyConfirmed` in [agent-client.mjs](../cli/src/agent-client.mjs)): a document that declares `prune` is planned first, the deletions are printed **before** the apply — the terminal is where the CLI's human sees them — and the token goes back with the write. Only pruning documents pay the extra round trip, and a prune that would delete nothing gets no token and needs none, so the flag alone is not the test.
- **SH109** — **Review queue** ([ShReviewService](../shio-app/src/main/java/com/viglet/shio/api/review/ShReviewService.java), [ShReviewAPI](../shio-app/src/main/java/com/viglet/shio/api/review/ShReviewAPI.java), [review.list.page.tsx](../shio-react/src/app/console/admin/review/review.list.page.tsx)). "The agent proposed N changes": the runs, what each one touched, and **approve** / **revert**. `GET /api/v2/review/sessions`, `/sessions/{id}`, `POST …/approve`, `POST …/revert` — an API, not a console-only feature (P1), console-authenticated and deliberately **not** on the agent namespace, because an agent's own credential should not be what approves its work.
  <br>**It is a view over the audit, not a proposal table.** A second copy of the content waiting to be accepted is the design the unified model already rejected: a post has a DRAFT row and a PUBLISHED row, and the draft *is* the proposal. So approve = publish the run's drafts (exactly the step SH107 keeps the agent from taking), and revert reuses SH14 restore and the SH55 trash. Nothing here is a third mechanism for saying what changed (P10).
  <br>**Revert is per entry and refuses to guess.** A `CREATE` is undone by trashing (recoverable, not purged), an `UPDATE` by restoring from the published snapshot, a `DELETE` by untrashing, a `PUBLISH` by unpublishing — and an entry with no honest undo, like an update to a post that was never published, is **reported with its reason** instead of approximated. The list walks newest-first so a create-then-publish pair ends as "unpublished, then trashed" rather than as a publish applied to a post that no longer exists. Every action is ACL-checked per post: reviewing is not a privilege.
  <br>The console page reuses the **SH14 diff dialog** unchanged, which only works because SH176 made the post read carry its post-type — before Block O the dialog had no schema to render.
- **SH110** (agent budget guards) **is not in this block**: per-session call/write/storage ceilings layer on SH45's per-tenant metering, and SH45 has not shipped. Building the ceiling first would mean a second metering mechanism to reconcile later.

## Block O — The human half (the console the curator uses, SH74)

> The product says the agent builds and the human curates. Block N made the console's *reads*
> agent-shaped; driving the finished surface end to end then showed the curating half did not
> work — a site an agent builds correctly could not be edited, previewed or opened. Every
> defect in this block answered `200`, which is why the block starts with an instrument
> (SH182) rather than a fix: without it these regress silently and a green probe on any route
> proves less than it appears to.

- **SH182** — **The console smoke check runs in CI** ([console-check.yml](../.github/workflows/console-check.yml), [e2e/provision.mjs](../shio-react/e2e/provision.mjs), [e2e/console-check.mjs](../shio-react/e2e/console-check.mjs)). The job packages the real jar (so the console under test is the one a release serves, no dev server involved), boots it, provisions a site from the SH94 `marketing-site` package — the one every Block O defect was reproduced against — and walks the routes in Chromium. Report and screenshots upload on pass and on fail, because "which page was blank" is the question a failure raises.
  <br>**Provisioning is a script, not shell in a YAML step**, because a clean instance is not walkable and neither reason is a console defect: the admin user is created with **no password** (first-access setup sets it) and there is no site at all. It does the three steps a human would — `POST /api/v2/setup`, `POST /api/v2/site`, then a blueprint apply — and it is idempotent, so it also works against a developer's running instance. The site-creation step does the full **CSRF dance** (fetch the token, keep the cookie, echo it back) rather than hiding it: that is exactly the friction **SH170** exists to remove, and writing it out keeps the cost visible instead of making it look free.
  <br>The check itself is unchanged and still discovers its targets from the agent surface, so it runs against any instance. Its two acknowledged debts stay open: it asserts *a* field renders, not the *right* field (a per-post-type expectation is the honest next step), and it has no accepted-findings baseline — **SH142**'s shape applies here unchanged.
- **SH176** — **The post read carries the post-type and parsed data** ([ShConsolePost](../shio-app/src/main/java/com/viglet/shio/api/post/unified/dto/ShConsolePost.java), [ShConsolePostMapper](../shio-app/src/main/java/com/viglet/shio/api/post/unified/ShConsolePostMapper.java), [ShConsolePostReadService](../shio-app/src/main/java/com/viglet/shio/api/post/unified/ShConsolePostReadService.java), [ShPostUnifiedAPITest](../shio-app/src/test/java/com/viglet/shio/api/post/unified/ShPostUnifiedAPITest.java)). `GET /post-unified/{id}` serialized the JPA entity, and the storage shape emptied the form twice over: the LAZY `shPostType` was never fetched so it arrived as `null`, and `data` is a `String` column so it arrived as a JSON *string* while the console's model declares an object. Every post edit page rendered zero fields, for every post-type, and would have rendered no values even with a schema. SH120's treatment applied to the read it skipped: a console DTO that composes the existing services, with `data` parsed and the post-type as its SH16 `ShPostTypeDef` — the same bytes `/api/v2/post-type/{name}` returns, so there is no third serialization of the model (P10).
  <br>**The writes moved with the reads.** `create`/`update`/`publish`/`restore`/`schedule`/`translate` returned the same entity, and the edit page rebinds its form from what a save returns — so fixing only the reads would have left the form working until the first save. They re-read through the read service rather than mapping the entity their own transaction returned, because that transaction has closed by the time the controller sees it: one extra query on a console write beats a response the form cannot bind to. `versions`, `listByFolder`, `trash` and `translations` had the same defect and are converted too.
  <br>**A field the post-type does not declare is named, not dropped** (`undeclaredFields`, rendered as a warning above the form). A projected object must not become a place values vanish into — the form cannot render such a field, saving still preserves it, and the honest thing is to say so. It is the read side of **SH168**; hiding it is how content gets lost.
- **SH177** — **`schemaJson` is retired** ([v2026.3.10.yaml](../shio-app/src/main/resources/db/changelog/v2026.3.10.yaml), `ShPostType`). A denormalized copy of the field list whose only writer was the one-shot `POST /api/v2/migration/unified/run`: correct exactly once, empty for every post-type a blueprint, `shio push` or the console's own editor created afterwards, stale for every type edited afterwards — a denormalization with no invalidation. The column is dropped, the migration service and its endpoint (its only writer) are deleted, and the console's `ShPostUnifiedMigrationService` goes with them. The model already carries `fields`; one shape is cheaper to keep right than two, and nothing read the column.
  <br>**The empty state it produced was wrong in three ways at once** — it named an internal migration in a curator-facing UI, prescribed a fix that could not work for a type created after the migration, and blamed the data when the cause was SH176. It now says the post-type declares no fields and offers the post-type editor.
- **SH178** — **One schema entry point for the form** ([post-unified.ts](../shio-react/src/models/post-unified/post-unified.ts)). The module exported `parseSchema` (no fallback) and `buildSchemaFromPostType` (with one) at equal prominence; the create page called the second and worked, the edit page called the first and rendered nothing. That single difference was the whole distance between "creating a post is fine" and "editing the post I just created is impossible", and it read as a content problem rather than a missing line. There is now one exported `postFormSchema()`, `parseSchema` is gone with the column it parsed, and the projection is private.
- **SH179** — **"View Site" goes somewhere that exists** ([site.list.page.tsx](../shio-react/src/app/console/content/site.list.page.tsx), [object.children.page.tsx](../shio-react/src/app/console/content/object.children.page.tsx), [routes.const.ts](../shio-react/src/app/routes.const.ts)). `ROUTES.PREVIEW` was declared and registered by nothing, and three call sites navigated to it — including both **View Site** buttons — so they rendered a blank page. This was the literal answer to "I cannot see the site".
  <br>**The two questions inside it are separated rather than conflated.** Reaching a *published* site is the CDA's business and depends on a front end the CMS does not own, so View Site opens the site's configured URL and says plainly when there is none — a legitimate answer where a blank page was not. Reaching a *draft* is Shio's own and already worked, so the per-post **View Page** mints an SH13 preview token, exactly as the editor's Preview Draft does, and it now only renders for posts (it was offered on folders too). The dead constant is deleted, so nothing can navigate there again.
- **SH180** — **An unknown console route says so** ([not-found.page.tsx](../shio-react/src/app/console/not-found.page.tsx), [App.tsx](../shio-react/src/App.tsx)). The SPA rendered a normal-looking, error-free empty page for any unmatched path, which is what made SH179 invisible in the product and what let a probe of a nonexistent route report success — a blank page and a working page were the same observation. A catch-all inside the console shell (so the user can navigate out of it) and one outside it name the path they could not match. The SH182 check's `unknown-route` probe asserts it, which is what makes every other probe's "ok" mean something.
- **SH181** — **The site read answers the key it is given** ([ShSiteAPI](../shio-app/src/main/java/com/viglet/shio/api/site/ShSiteAPI.java), [ShSiteResolveTest](../shio-app/src/test/java/com/viglet/shio/api/site/ShSiteResolveTest.java), [visual-editor.page.tsx](../shio-react/src/app/console/universal-editor/visual-editor.page.tsx)). Opening the Universal Editor issued `GET /api/v2/site/{furl}` against an id-keyed endpoint and 404'd twice before rendering. `GET /{id}` now resolves id → furl → name, in that order so the declared key wins a collision; **the writes deliberately do not** — a read that resolved a near-miss shows the curator the wrong site, a write that did would change it. The guard is a test rather than a patched call site, because this is the third instance of one confusion (SH117 settled id-versus-name for post-types) and §VIII.10's rule is a guard per invariant.
  <br>The editor also **reports a failed resolve** instead of spinning: a site with no front-end URL configured renders a sentence and a way back, which is the SH180 lesson at page level.

Three behavioural changes vs SH40: (1) a **format-only** request (no `w`/`h`) is no longer a no-op — it transcodes at the original size; (2) the served **content type changes** with the format (the `/api/v2/staticfile/{id}` controller already set it from the result; the public `/file_source/**` path derives `Content-Type` from the file name, so [ShImageTransformResourceTransformer](../shio-app/src/main/java/com/viglet/shio/api/staticfile/transform/ShImageTransformResourceTransformer.java) now wraps the bytes in an `HttpResource` that pins the result's content type as a response header — overriding the `.jpg`-name guess for a jpeg→webp conversion); (3) converting an image **with alpha** to a format that can't carry it (jpeg/bmp) flattens onto a white background first, otherwise the alpha channel garbles the colours. **webp output works** via the new `org.sejda.imageio:webp-imageio` SPI (bundles native libwebp for win/mac/linux, registered through `META-INF/services`); jpeg/png/gif/bmp ride the existing ImageIO/jai-imageio writers. **avif** has no mature Java writer, so `?format=avif` (still accepted by the SH39 allow-list) falls through the same graceful path as any writer-less target → original bytes in the source format, never a 500. - **SH42** — **Image-transform result cache (disk/memory, ETag, tenant-aware).** A transform (decode → resize/crop → re-encode, SH40/SH41) is pure but expensive, and a given `source + ?w=&h=&format=&crop=` always yields the same bytes — so memoise them. **Caching decorator:** new [ShCachingImageTransformPipeline](../shio-app/src/main/java/com/viglet/shio/api/staticfile/transform/ShCachingImageTransformPipeline.java) is now the `@Primary` [ShImageTransformPipeline](../shio-app/src/main/java/com/viglet/shio/api/staticfile/transform/ShImageTransformPipeline.java) (the SH40 [ShThumbnailatorImageTransformPipeline](../shio-app/src/main/java/com/viglet/shio/api/staticfile/transform/ShThumbnailatorImageTransformPipeline.java) drops `@Primary` and becomes the injected delegate), so **both** delivery routes — the `/api/v2/staticfile/{id}` controller and the `/file_source/**` resource transformer, which already inject the primary bean — go through the cache transparently. **Store:** [ShImageTransformCache](../shio-app/src/main/java/com/viglet/shio/api/staticfile/transform/ShImageTransformCache.java) is a size-bounded in-memory LRU (`Collections.synchronizedMap` over an access-ordered `LinkedHashMap` with `removeEldestEntry`) in front of a disk cache rooted at [ShImageCacheProperties](../shio-app/src/main/java/com/viglet/shio/property/ShImageCacheProperties.java)`.path` (`shio.image-cache.path`, default `store/image_cache`; `.enabled`, `.max-memory-entries`). The **key** is a hex SHA-256 over `tenant | filename | lastModified | length | w | h | format | crop` — the source identity is the HTTP weak-validator triple (name + mtime + size), so a re-upload that changes the bytes lands on a fresh key (old entries orphan; disk pruning is left to ops, not done here). Each entry is two files: `<hash>` (bytes) + `<hash>.ct` (content type); disk I/O is best-effort — a read/write failure degrades to a miss / no-store and is logged, never thrown, so a broken cache can't break delivery. **Tenant-aware (SH22):** the current [ShTenantContext](../shio-app/src/main/java/com/viglet/shio/tenant/ShTenantContext.java) tenant (default `shio`) is the first key component **and** the disk sub-directory (`<root>/<tenant>/<hash>`), so tenant A and B never share a cached entry or an ETag even for an identical source path + params. **ETag / 304:** the key doubles as a stable strong ETag stamped onto the [ShImageTransformResult](../shio-app/src/main/java/com/viglet/shio/api/staticfile/transform/ShImageTransformResult.java) (new third record component + back-compat two-arg ctor + `withEtag`); the controller emits `ETag` and answers `If-None-Match` with `304 Not Modified`, and the public `/file_source/**` path does the same via a `setEtagGenerator` on the resource handler ([ShStaticResourceConfiguration](../shio-app/src/main/java/com/viglet/shio/spring/ShStaticResourceConfiguration.java)) reading the ETag off the SH41 [ShImageTransformResourceTransformer](../shio-app/src/main/java/com/viglet/shio/api/staticfile/transform/ShImageTransformResourceTransformer.java)`.ShTransformedImageResource`. **Empty (serve-original) results are never cached** — a decline (non-image, writer-less target, I/O failure) must stay re-evaluable so a later transformable upload at the same id isn't poisoned by a negative entry; a disabled cache is a thin pass-through that stamps no ETag. 12 new tests (8 [ShImageTransformCacheTest](../shio-app/src/test/java/com/viglet/shio/api/staticfile/transform/ShImageTransformCacheTest.java) — key stability/variance/tenant-scoping, memory+disk round-trip, cross-instance disk read, tenant-prefixed layout; - **SH43** — **Image-transform limits & security (max dims, allowed formats, signed URLs) — completes the SH25 epic.** The transform surface (SH39–42) was an open door: any caller could request arbitrary `?w=&h=&format=` combinations, pinning CPU and flooding the SH42 cache, and a tiny but enormously-dimensioned upload could OOM the decoder.
